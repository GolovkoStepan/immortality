# Состояние и восстановление

## 1. Где что лежит

### В репозитории (`.agent/`, под git)

Человекочитаемое и ревьюируемое. Переживает перенос проекта, видно в diff.

| Файл | Содержание | Кто пишет |
| --- | --- | --- |
| `PLAN.md` | Декомпозиция, стратегия, порядок работ | planner, человек |
| `ACCEPTANCE.md` | Критерии приёмки и команды проверки | planner, человек |
| `TASKS.json` | Дерево задач и подзадач, статусы, DoD | агент |
| `DECISIONS.md` | Принятые решения и обоснования | агент, человек |
| `NOTES.md` | Рабочая память: факты, ограничения, **отвергнутые гипотезы** | агент |
| `JOURNAL.jsonl` | Append-only журнал событий | агент |

`TASKS.json` валидируется целиком при загрузке (`core::plan`): цикл, висячая или
самоссылка, дубль id, `DoD` без гейта, объявленный `depth`, расходящийся с вложенностью, и
ребёнок, зависящий от предка, отвергаются до первого шага (D-075). Правка файла человеком
подхватывается по `(mtime, len)` без рестарта; битая правка — ошибка, а не тихий откат к
предыдущей версии.

Дробление подзадачи (L4) — единственная операция, которая меняет **форму** дерева, а не
только статус, поэтому у неё свои правила (D-078): дочерние `DoD` наследуются, обязательные
проверки и ревью родителя должны сохраниться, глубина не растёт за `max_subtask_depth`.
Проверка идёт до мутации, так что отказ не оставляет ни полузаписанного `TASKS.json`, ни
строки `subtask_split` в журнале.

### Вне репозитория (`~/Library/Application Support/immortality/`)

Машинное и тяжёлое. Можно потерять (кроме эскалаций), можно перестроить.

```
config.toml              # глобальный конфиг, политики (human-only)
daemon.lock              # pid + старт, защита от второго демона
daemon.sock              # 0600
daemon.token             # 0600, аутентификация клиента
index.db                 # индекс/кэш (rebuildable)
registry.json            # проекты: id, путь, remote (D-070)
state/<project>/<task>/
    config_snapshot.toml
    subtasks.json
    attempts.json
    panic.json           # если был аварийный останов
    escalations.json
    transcripts/2026-11.jsonl
artifacts/<sha256>       # content-addressed tool output, дедуп
logs/2026-11.log         # активный месяц, plain
logs/2026-10.log.gz      # архивы по месяцам
```

`index.db` — кэш для быстрых запросов (`status`, `log`), перестраивается из журнала при
несовпадении версии схемы или повреждении. Источник истины — файлы.

## 2. Журнал событий

Одна строка — одно событие. Запись атомарна: строка целиком + `\n` + `fsync`.
Ротация по размеру сегмента (8 MiB): `JOURNAL.2026-11-12T10-00-00.jsonl`.

```jsonc
{
  "v": 1,
  "seq": 18432,                       // монотонный, на задачу
  "ts": "2026-11-12T10:14:03.221Z",
  "task": "tsk_01JB...",
  "subtask": "sub_03",
  "attempt": 2,
  "kind": "tool_call_completed",      // см. таблицу ниже
  "payload": { "...": "..." },
  "artifact": "sha256:9f2c...",       // если payload вынесен в artifacts/
  "prev": "sha256:1a7b..."            // хэш предыдущей записи (цепочка)
}
```

`subtask` и `attempt` — не украшение. Recovery группирует попытки по паре
`(subtask, attempt)`, чтобы найти те, что крах оставил `Running`; запись без области для
него невидима, и попытка осталась бы открытой навсегда. Поэтому runner пишет журнал через
`Journal::append_scoped` и `ToolCallLog::scoped`, а не через бесхозный `append_event`, и
тест требует области у **каждой** записи прогона. Записи о задаче целиком (старт демона,
усечение хвоста) области не имеют и не сериализуют эти поля вовсе — `null` и «отсутствует»
читались бы потребителями по-разному.

`kind` (закрытый список; расширение — только с повышением `v`):

| kind | Когда |
| --- | --- |
| `task_created`, `task_state` | жизненный цикл |
| `plan_written`, `plan_edited`, `plan_approved` | планирование |
| `subtask_state` | смена состояния подзадачи |
| `subtask_split` | дробление: родитель в `Skipped`, дети в `Pending`; пишется **после** `TASKS.json`, чтобы крах между записями оставлял корректное дерево, а не журнал о несуществующих детях (D-078) |
| `attempt_started`, `attempt_failed`, `attempt_restarted` | попытки |
| `model_request`, `model_response`, `model_stream_aborted` | инференс (метаданные; тело — в artifacts) |
| `native_toolcall`, `text_fallback`, `invalid_toolcall` | качество протокола |
| `tool_call_intent` | **до** исполнения: имя, аргументы, idempotency, ожидаемый эффект |
| `tool_call_started` | процесс запущен |
| `tool_call_completed` / `tool_call_failed` | результат (тело — в artifact) |
| `tool_call_unknown` | процесс умер, эффект неизвестен |
| `effect_verified` / `effect_absent` | результат probe после сбоя |
| `checkpoint_created` | git-чекпоинт и его SHA |
| `detector_fired` | `d1`…`d5`, уровень `l1`…`l3`, счётчик-метрика; одна запись на шаг (D-077) |
| `compaction` | компактация контекста |
| `gate_result` | один гейт: тег `gate` — `sanity` (находки), `check` (id, команда, код, длительность, required), `review` (одобрено, проблемы) или `verdict` (прошло, причина, почему). Вердикт всегда последний; `gate: verdict` + `passed: true` закрывает попытку и в recovery (D-079) |
| `escalation_opened`, `escalation_resolved` | очередь эскалаций (D-067) |
| `backend_unavailable`, `backend_restored` | сеть/бэкенд |
| `cache_stats` | `cache_n` / `prompt_n` на запрос — метрика здоровья кэша |
| `daemon_started`, `daemon_stopped`, `daemon_recovered` | жизненный цикл демона |

Цепочка `prev` даёт обнаружение подмены/повреждения и точную точку обрыва.

## 3. Протокол tool-call: три записи

Каждый вызов инструмента проходит журнал трижды:

```
tool_call_intent    → id, tool, args_hash, idempotency, expected_effect
tool_call_started   → pid/handle (если применимо)
tool_call_completed → exit_code, output_artifact, duration
```

Правило: **результат записывается в журнал до того, как его увидит модель.** Иначе
восстановление после сбоя невозможно: модель «помнит» результат, которого нет на диске,
или наоборот.

### Идемпотентность

| Инструмент | Класс | Действие при обрыве после `started` |
| --- | --- | --- |
| `read_file`, `glob`, `grep`, `read_state`, `grep_journal` | idempotent | повторить молча |
| `update_state` | by-content | перечитать файл; совпал — считать выполненным (D-065) |
| `write_file`, `edit_file` | idempotent-by-content | перечитать файл; если контент совпал — считать выполненным |
| `shell` (read-only классифицированные) | idempotent | повторить |
| `shell` (mutating) | unknown | **не повторять**; probe: состояние рабочего дерева, наличие ожидаемого файла |
| `git commit` (модельный) | unknown | probe: искать коммит по trailer `Immortality-Call: <call-id>` (D-063); nonce попытки — только у системных коммитов |
| `start_process` | unknown | probe: поиск процесса по маркеру в командной строке (D-061) |
| `escalate` | idempotent по ключу | дедуп по `escalation_key` |
| `delegate` | unknown | probe: есть ли отчёт субагента по id (D-068) |

Каждый инструмент реализует `probe(record) -> Applied | NotApplied | Unknown`. При
`NotApplied` — повтор; при `Applied` — синтетическое observation «эффект уже достигнут»;
при `Unknown` — эскалация уровня L3 (перезапуск попытки с откатом к чекпоинту).

`delegate` — единственный вызов, который тратит целый бюджет субагента, поэтому его probe
устроен строже остальных:

- id отчёта выводится из `call_id` (`del_` + 16 hex от `sha256(call_id)`), а не хранится:
  после падения у recovery есть только `intent` из журнала. Аргументы в журнале могут быть
  вынесены в artifact, а `call_id` — нет.
- отчёт не может называться `call_id`: он приходит от модели, а значит может содержать `/`,
  `..` или килобайты текста. Имя файла, выбранное моделью, — это directory traversal.
- `Applied` = файл отчёта читается; `NotApplied` = файла нет; **`Unknown` = файл есть, но не
  парсится**. Повреждённый отчёт — не отсутствие: признать его `NotApplied` значит повторить
  уже выполненный прогон и потратить бюджет дважды.
- отчёт пишется **до** возврата инструмента и до журнальной записи о результате. Отчёт при
  этом пишется и для провалившегося прогона (`exhausted`, `failed`): субагент действительно
  работал, и повторять его нельзя. Не пишется только при ошибке запуска — тогда
  `NotApplied` корректен.
- повторный вызов с тем же `call_id` (retry recovery или повтор модели) отвечает из файла и
  **не запускает** субагента. Это отдельная от probe защита: probe спрашивает, а инструмент
  обязан не выполнить работу дважды, даже когда recovery решил повторить.

## 4. Чекпоинты

Два независимых уровня:

1. **Скрытые** — на каждую успешную подзадачу и перед каждым рискованным действием
   (мутирующая shell-команда, `git`-операция, правка более N файлов).
   Механизм: временная ветка `agent-ckpt/<task-id>` (или `git stash create` там, где это
   уместно), SHA пишется в журнал событием `checkpoint_created`. В историю задачи не
   попадает.
2. **Содержательные** — коммиты в `agent/<task-id>` по завершении подзадачи, Conventional
   Commits, в теле ссылка на `task/subtask` и на nonce попытки.

Откат (L3) = `git reset --hard <ckpt-sha>` в worktree задачи + восстановление состояния
подзадачи к последнему консистентному снимку. Мгновенно и без мусора в истории.

Перед `git reset --hard` незакоммиченные изменения складываются в `git stash` с меткой
попытки, чтобы не потерять данные, которые могут пригодиться.

## 5. Восстановление после креша

Демон стартует и выполняет процедуру `recover()` для каждой незавершённой задачи:

1. **Прочитать журнал** до конца. Если последняя строка обрезана — отбросить её (это
   гарантированно недописанная запись, потому что запись атомарна), записать событие
   `journal_truncated_tail` с числом байт.
2. **Проверить цепочку `prev`**. Разрыв — не пытаться «чинить» молча: задача → `blocked`
   с причиной `journal_corrupt`, копия журнала сохраняется, эскалация человеку.
3. **Найти незакрытые tool-call'ы**: `intent`/`started` без `completed`/`failed`.
   - idempotent → перезапустить;
   - unknown → выполнить `probe`; результат записать как `effect_verified` / `effect_absent`
     и подложить модели как observation;
   - `Unknown` → L3 (откат к чекпоинту и новая попытка).
4. **Проверить worktree**: существует ли, на каком SHA, есть ли незакоммиченные изменения.
   Если worktree потерян — пересоздать из `agent/<task>`; если ветки нет — из базовой ветки
   и `checkpoint_created` последнего чекпоинта.
5. **Сверить состояние подзадач** с файлами: `attempts.json` vs журнал. Победитель — журнал.
6. **Записать** `daemon_recovered` с описанием, что именно пришлось чинить.
7. Продолжить с места остановки: следующая подзадача или новая попытка текущей.

Всё это покрыто тестами-симуляторами с инъекцией падения в каждой точке протокола
(между `intent` и `started`, между `started` и `completed`, во время записи журнала,
во время `git commit`).

## 6. Бэкенд недоступен

- Health-check каждые 30 с (дешёвый `GET /v1/models`), плюс реакция на ошибки в запросах.
- Ошибки инференса делятся на: `retryable` (таймаут, 429, 5xx, обрыв стрима) и
  `fatal` (400 на схему/невалидный запрос). Для `retryable` — экспоненциальный backoff
  `1s → 2s → 4s … max 60s`, до 6 попыток на шаг.
- Отдельный класс `model_failure`: 200 с `finish_reason: length` и пустым `content`
  (модель потратила бюджет на reasoning) или пустой ответ без tool-calls. Лечится retry
  с увеличенным `max_tokens` и отключённым reasoning, а не backoff'ом.
- Проверено на живом бэкенде: 502 может прийти после 300 с prefill на промпте 130K —
  это `retryable`, не `fatal`.
- Пока бэкенд лежит: задача → `waiting_backend`, но **работа не останавливается**:
  выполняются отложенные проверки, тесты, коммиты, обновление состояния. Планировщик
  берёт другую задачу, если та не требует модели.
- Через 15 мин непрерывной недоступности — эскалация `backend_unavailable` (macOS-нотификация),
  но задача остаётся в `waiting_backend` и повторяет попытки при восстановлении.

## 7. Рост данных

- `JOURNAL.jsonl` не удаляется никогда: компактный, основной аудит-след.
- Тяжёлые тела (вывод инструментов, тела ответов модели) — в `artifacts/<sha256>`,
  дедуплицируются, TTL 30 дней, чистятся `immortality gc`.
- Транскрипты: файл на месяц, TTL 30 дней.
- Логи: текущий месяц — plain, по наступлении нового месяца предыдущий сжимается в
  `logs/YYYY-MM.log.gz`. Ретенция архивов — 12 месяцев (настраиваемо).
- `gc` отказывается удалять артефакты, на которые ссылается журнал незавершённой задачи.
- Порог свободного места (1 GiB): при проломе — предупреждение, при 256 MiB — задача
  переводится в `paused_disk`, эскалация. Молча упасть от ENOSPC система не должна.
