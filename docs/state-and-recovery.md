# Состояние и восстановление

## 1. Где что лежит

### В репозитории (`.agent/`, под git)

Человекочитаемое и ревьюируемое. Переживает перенос проекта, видно в diff.

| Файл | Содержание | Кто пишет |
| --- | --- | --- |
| `PLAN.md` | Декомпозиция, стратегия, порядок работ | planner, человек |
| `ACCEPTANCE.md` | Критерии приёмки и команды проверки | planner, человек |
| `TASKS.json` | Дерево задач и подзадач, статусы, DoD | агент |
| `DECISIONS.md` | Принятые решения и обоснования | агент, человек |
| `NOTES.md` | Рабочая память: факты, ограничения, **отвергнутые гипотезы** | агент |
| `JOURNAL.jsonl` | Append-only журнал событий | агент |

`TASKS.json` валидируется целиком при загрузке (`core::plan`): цикл, висячая или
самоссылка, дубль id, `DoD` без гейта, объявленный `depth`, расходящийся с вложенностью, и
ребёнок, зависящий от предка, отвергаются до первого шага (D-075). `Plan::refresh` сравнивает
`(mtime, len)` и перечитывает файл — но в демоне его никто не зовёт: план грузится один раз при
`start`, поэтому правка на диске посреди прогона вступает в силу со следующего `start`, а не с
следующей подзадачи. Битая правка — ошибка при загрузке, а не тихий откат к предыдущей версии.

Дробление подзадачи (L4) — единственная операция, которая меняет **форму** дерева, а не
только статус, поэтому у неё свои правила (D-078): дочерние `DoD` наследуются, обязательные
проверки и ревью родителя должны сохраниться, глубина не растёт за `max_subtask_depth`.
Проверка идёт до мутации, так что отказ не оставляет ни полузаписанного `TASKS.json`, ни
строки `subtask_split` в журнале.

### Вне репозитория (`~/Library/Application Support/immortality/`)

Машинное и тяжёлое. Можно потерять (кроме эскалаций), можно перестроить.

```
config.toml                   # глобальный конфиг, политики (human-only)
daemon.lock                   # pid держателя, защита от второго демона
daemon.sock                   # 0600
daemon.token                  # 0600, аутентификация клиента
registry.json                 # проекты: id, путь, remote (D-070)
state/<project>/<task>/
    subtasks.json             # кэш состояний подзадач
    attempts.json             # кэш попыток и их бюджетов
    panic.json                # причина блока, когда журнал нечитаем (D-082)
    escalations.json          # очередь вопросов человеку
    processes/                # реестр фоновых процессов задачи
    delegations/<del_…>.json  # отчёты субагентов (D-068)
artifacts/<sha256>            # content-addressed tool output, дедуп
logs/2026-11.log              # активный месяц, plain
logs/2026-10.log.gz           # архивы по месяцам
```

Быстрый `status` **не** читает `attempts.json` и `subtasks.json`: файлы — производные кэши,
которые переписываются из журнала при расхождении (§6), а `status` идёт по реестру и журналам
проектов (`journal_summary`, число эскалаций и делегаций) и только потом считает `scheduling`.
Продюсеры кэша — стартовое восстановление и сам `recovery`; читателя, кроме них и тестов, нет.
Отдельной базы или индекса в v0.1 нет: `StatePaths::index_db` — зарезервированный путь, его не
пишет ни один код. Источник истины — журнал и файлы `.agent/` в репозитории.

## 2. Журнал событий

Одна строка — одно событие. Запись атомарна: строка целиком + `\n` + `fsync`.
Ротация по размеру сегмента (8 MiB): `JOURNAL.2026-11-12T10-00-00.123.jsonl` (при совпадении
метки времени в ту же миллисекунду к имени добавляется `-001`).

```jsonc
{
  "v": 1,
  "seq": 18432,                       // монотонный, на файл/сегмент: общий для всех задач проекта
  "ts": "2026-11-12T10:14:03.221Z",
  "task": "tsk_01JB...",
  "subtask": "sub_03",
  "attempt": 2,
  "kind": "tool_call_completed",      // см. таблицу ниже
  "payload": { "...": "..." },
  "artifact": "sha256:9f2c...",       // если payload вынесен в artifacts/
  "prev": "sha256:1a7b..."            // хэш предыдущей записи (цепочка)
}
```

`subtask` и `attempt` — не украшение. Recovery группирует попытки по паре
`(subtask, attempt)`, чтобы найти те, что крах оставил `Running`; запись без области для
него невидима, и попытка осталась бы открытой навсегда. Поэтому runner пишет журнал через
`Journal::append_scoped` и `ToolCallLog::scoped`, а не через бесхозный `append_event`, и
тест требует области у **каждой** записи прогона. Записи о задаче целиком (старт демона,
усечение хвоста) области не имеют и не сериализуют эти поля вовсе — `null` и «отсутствует»
читались бы потребителями по-разному.

`ts` приходит не с машинных часов, а с часов **журнала**: `Journal` держит
`Arc<dyn Clock>`, runner ставит туда свои на входе в попытку (`set_clock`). Поэтому записи
раннера, `ToolCallLog` и ротации сегментов упорядочены одним источником, а симулятор
подставляет замороженные часы и получает воспроизводимый журнал. Golden-файл сравнивается
нормализованным: `ts` → `dt_ms` (смещение от фикстуры), attempt-ULID → `att_1`, `att_2`
(D-081).

`kind` (закрытый список; расширение — только с повышением `v`):

| kind | Когда |
| --- | --- |
| `task_created`, `task_state` | жизненный цикл |
| `plan_written`, `plan_edited`, `plan_approved` | планирование: сегодня это **триггеры домена** (`TaskTrigger` в `core::domain::task`), а не записи журнала — см. оговорку ниже |
| `subtask_state` | смена состояния подзадачи |
| `subtask_split` | дробление: родитель в `Skipped`, дети в `Pending`; пишется **после** `TASKS.json`, чтобы крах между записями оставлял корректное дерево, а не журнал о несуществующих детях (D-078) |
| `attempt_started`, `attempt_failed`, `attempt_restarted` | попытки; у `attempt_restarted` поле `attempt` — закрываемая попытка, номер замены в payload (`next`), там же `cause`, `why`, `base` (D-027, D-080) |
| `model_request`, `model_response`, `model_stream_aborted` | инференс (метаданные; тело — в artifacts). Пишутся `model_response` и `model_stream_aborted`; у `model_request` продюсера нет |
| `native_toolcall`, `text_fallback`, `invalid_toolcall` | качество протокола. Пишется только `invalid_toolcall`; два первых объявлены, но их никто не порождает |
| `tool_call_intent` | **до** исполнения: `call`, `tool`, `idempotency`, `args_digest`, `expected_effect` и **вложенный** `arguments` — аргументы инструмента не лежат рядом с метаданными, иначе аргумент с именем `tool` выдал бы себя за поле записи (D-081) |
| `tool_call_started` | процесс запущен |
| `tool_call_completed` / `tool_call_failed` | результат (тело — в artifact) |
| `tool_call_unknown` | процесс умер, эффект неизвестен |
| `effect_verified` / `effect_absent` | результат probe после сбоя; пишет их `ToolCallLog::effect` по решению восстановления, `Unknown` вердиктом не записывается |
| `checkpoint_created` | git-чекпоинт, его SHA и `role` (`base` / `discarded` / `rollback` / `preserved` / `recovery`); `rollback` без последующего `attempt_restarted` — незавершённый откат (D-080) |
| `detector_fired` | `d1`…`d6`, уровень `l1`…`l3`, счётчик-метрика; одна запись на шаг (D-077) |
| `compaction` | объявлен, но ещё не порождается: компактации контекста в v0.1 нет |
| `gate_result` | один гейт: тег `gate` — `sanity` (находки), `check` (id, команда, код, длительность, required), `review` (одобрено, проблемы) или `verdict` (прошло, причина, почему). Вердикт всегда последний; `gate: verdict` + `passed: true` закрывает попытку и в recovery (D-079) |
| `escalation_opened`, `escalation_resolved` | очередь эскалаций (D-067) |
| `backend_unavailable`, `backend_restored` | сеть/бэкенд |
| `cache_stats` | объявлен, но не порождается: метрика здоровья кэша пока не считается |
| `daemon_started`, `daemon_stopped`, `daemon_recovered` | жизненный цикл демона |

Оговорка к таблице: перечисление шире того, что реально пишется. Проверка «кто вызывает
`Kind::X` в прод-коде» даёт для `plan_written`/`plan_edited`/`plan_approved`, `model_request`,
`native_toolcall`, `text_fallback`, `compaction`, `cache_stats` пустой ответ — эти имена
зарезервированы под будущие продюсеры и появляются только в тестах и в таблице `Kind::ALL`.
Живой журнал (три прогона `black_jack`) содержит ровно: `task_created`, `task_state`,
`subtask_state`, `attempt_started`, `attempt_failed`, `attempt_restarted`, `model_response`,
`invalid_toolcall`, `tool_call_intent`, `tool_call_started`, `tool_call_completed`,
`tool_call_failed`, `checkpoint_created`, `detector_fired`, `gate_result`, `daemon_started`,
`daemon_stopped`, `daemon_recovered`. Список закрыт: новый `kind` — только с повышением `v`.

Цепочка `prev` даёт обнаружение подмены/повреждения и точную точку обрыва.

## 3. Протокол tool-call: три записи

Каждый вызов инструмента проходит журнал трижды:

```jsonc
// tool_call_intent — запись целиком, метаданные из типа `Intent`, аргументы вложены
{"call":"call_7","tool":"write_file","idempotency":"by_content",
 "args_digest":"sha256:…","expected_effect":"write src/parser.rs",
 "arguments":{"path":"src/parser.rs","content":"…"}}

// tool_call_started  → pid/handle (если применимо)
// tool_call_completed → exit_code, output_artifact, duration
```

Метаданные пишет сам `ToolCallLog::intent` из `Intent`, а не call-site: одна точка владеет
схемой записи, и забыть поле нельзя. `expected_effect` — про **этот** вызов («write
src/parser.rs», «run `cargo test`»), а не описание инструмента; recovery цитирует эту фразу
оператору, когда не может понять, подействовал ли вызов, и `immortality log` показывает её
до запуска. Чтение терпит старые записи: без `idempotency` — `Unknown` (самый опасный класс),
без `expected_effect` — пустая строка (D-081).

Правило: **результат записывается в журнал до того, как его увидит модель.** Иначе
восстановление после сбоя невозможно: модель «помнит» результат, которого нет на диске,
или наоборот.

### Идемпотентность

| Инструмент | Класс в коде | Действие при обрыве после `started` |
| --- | --- | --- |
| `read_file`, `glob`, `grep`, `read_state`, `grep_journal` | `Idempotent` | повторить молча |
| `update_state` | `ByContent` | перечитать файл; совпал — считать выполненным (D-065) |
| `write_file`, `edit_file` | `ByContent` | перечитать файл; если содержимое совпало — считать выполненным |
| `shell` (любой, включая read-only-классифицированный) | `Unknown` | **не повторять**; probe смотрит на дерево (D-026) |
| `git`, кроме `commit` | `Idempotent` | повторить: второй `add` равен первому, повторный `stash` ничего не теряет |
| `git commit` (модельный) | `Unknown` | probe: искать коммит по trailer `Immortality-Call: <call-id>` (D-063) |
| `start_process` | `Unknown` | probe: поиск процесса по маркеру в командной строке (D-061) |
| `read_process` | `ByContent` | перечитать; чтение двигает курсор, поэтому не `Idempotent` |
| `kill_process` | `Idempotent` | повторить: второй `kill` уже мёртвого процесса — не второй эффект |
| `escalate` | `ByContent` | дедуп по `key`: повтор отвечает из очереди |
| `delegate` | `Unknown` | probe: есть ли отчёт субагента по id (D-068) |

`shell` — `Unknown` для **любой** команды: `cargo test` пишет в `target/`, и упавший вызов
неотличим от несостоявшегося (D-026). Класс не выводится из классификатора эффектов: тот
решает, нужен ли гейт, а не можно ли повторять.

Каждый инструмент реализует `probe(record) -> Applied | NotApplied | Unknown`. При
`NotApplied` — повтор; при `Applied` — синтетическое observation «эффект уже достигнут»;
при `Unknown` — эскалация уровня L3 (перезапуск попытки с откатом к чекпоинту).

`delegate` — единственный вызов, который тратит целый бюджет субагента, поэтому его probe
устроен строже остальных:

- id отчёта выводится из `call_id` (`del_` + 16 hex от `sha256(call_id)`), а не хранится:
  после падения у recovery есть только `intent` из журнала. Аргументы в журнале могут быть
  вынесены в artifact, а `call_id` — нет.
- отчёт не может называться `call_id`: он приходит от модели, а значит может содержать `/`,
  `..` или килобайты текста. Имя файла, выбранное моделью, — это directory traversal.
- `Applied` = файл отчёта читается; `NotApplied` = файла нет; **`Unknown` = файл есть, но не
  парсится**. Повреждённый отчёт — не отсутствие: признать его `NotApplied` значит повторить
  уже выполненный прогон и потратить бюджет дважды.
- отчёт пишется **до** возврата инструмента и до журнальной записи о результате. Отчёт при
  этом пишется и для провалившегося прогона (`exhausted`, `failed`): субагент действительно
  работал, и повторять его нельзя. Не пишется только при ошибке запуска — тогда
  `NotApplied` корректен.
- повторный вызов с тем же `call_id` (retry recovery или повтор модели) отвечает из файла и
  **не запускает** субагента. Это отдельная от probe защита: probe спрашивает, а инструмент
  обязан не выполнить работу дважды, даже когда recovery решил повторить.

## 4. Чекпоинты

Два независимых уровня:

1. **Скрытые** — `agent-ckpt/<task-id>`, сила-ветка, которую двигает каждый снимок. Пишет
   только `daemon::GitCheckpoints::hidden_checkpoint`: `git add --all` + `git write-tree` +
   `git commit-tree`, без видимого индекса и без `git stash` (`git stash create` писал бы в
   общий stash пользователя и отказывался бы при чистом дереве — модульные доки
   `core::checkpoint`). Продюсеров у `checkpoint_created` два модуля и пять ролей: `runner`
   (`base` перед первой попыткой, `discarded` и `rollback` перед `reset`) и
   `daemon::recovery` (`preserved`, `discarded` и `recovery` при старте). «Перед каждым
   рискованным действием» — это цель дизайна, а не сегодняшнее поведение: гейт рискованного
   вызова снимок не берёт.
2. **Содержательные** — коммиты в `agent/<task-id>`. `GitRepo::meaningful_commit` (Conventional
   Commit + трейлер `Attempt: <nonce>`) реализован и покрыт тестами, но в проде его не зовёт
   никто: коммит на закрытии подзадачи делает **модель** через инструмент `git`
   (`subcommand: "commit"`), и трейлер у такого коммита — `Immortality-Call: <call-id>`, а не
   nonce попытки. Именно поэтому probe для `git commit` ищет call-id (D-063).

Откат (L3) = `git reset --hard <ckpt-sha>` в worktree задачи + восстановление состояния
подзадачи к последнему консистентному снимку. Мгновенно и без мусора в истории.

Незакоммиченная работа **не теряется**: перед `reset --hard` раннер пишет её в скрытый
чекпоинт и записывает SHA в журнал. Порядок жёсткий — **снимок, журнал, перемещение**:

| `role` в `checkpoint_created` | Когда | Что значит |
| --- | --- | --- |
| `base` | перед **первой попыткой** подзадачи (`capture_base` в `AttemptSession::drive`) | дерево, к которому возвращаются все последующие откаты |
| `discarded` | перед `reset` | работа, которую откат вот-вот выбросит; `None` при чистом дереве — записи нет |
| `rollback` | перед `reset`, после `discarded` | маркер: «дерево сейчас будет сброшено на этот SHA» |
| `preserved` | recovery при старте, до любого пробера | незакоммиченная работа, найденная после краха |
| `recovery` | recovery перед своим `reset` | откат по решению восстановления, без `attempt_restarted` |

`base` снимается до первой попытки намеренно. Снятый внутри откатa, он содержал бы работу
провалившейся попытки: ветка сбрасывалась бы на неё, откат ничего бы не выбрасывал, и
`git diff HEAD` у ревьюера был бы пустым. Это измеренный дефект, а не гипотеза — в живом
прогоне три записи `checkpoint_created` одного перезапуска называли один и тот же SHA.

`preserved` и `recovery` пишет не раннер, а исполнитель восстановления. `rollback` от них
отличается смыслом: он обещает, что следом придёт `attempt_restarted`, подтверждающий
перемещение. У восстановления такого подтверждения нет — попытку оно закрывает отдельным
шагом, и `rollback` там означал бы «следующий старт считает этот откат прерванным».

`attempt_restarted` пишется **после** `reset`. Если на диске есть `rollback` и нет
`attempt_restarted` для той же пары `(subtask, attempt)`, крах случился внутри откатa:
recovery планирует `RollbackToCheckpoint` на названный SHA, а `rolling_back` добавляет
`AbandonAttempt`. Так окно «маркер записан — дерево не переехало или переехало» перестаёт
быть невидимым.

## 5. Где лежит журнал

Журнал, план и рабочая память — в `.agent/` **проекта**, а не в worktree. Работа с состоянием
идёт через `PolicyGate::with_project_agent_dir`: `read_state`, `update_state` и `grep_journal`
адресуют проектный каталог, потому что worktree-копия `.agent/` — снимок с момента создания
ветки и устарела по построению. Измерено на фикстуре `word-count`: проектный `TASKS.json`
говорил `done`/`blocked`, worktree-копия — `pending` обо всех подзадачах (D-103).

Сам worktree задачи стоит отдельным каталогом (`<parent>/<name>-agent/<task>`). Разделение
обязательно, а не косметика: откат L3 делает `git reset --hard` в worktree, и журнал внутри
него был бы стёрт тем самым восстановлением, которое его читает. Это не гипотеза — тестовая
фикстура с журналом внутри worktree падала именно так, и фикстура теперь повторяет
продакшен-раскладку.

Следствие для порядка операций: журнал читается **до** открытия на запись, потому что
`Journal::open` обрезает оборванный хвост. План, построенный после открытия, хвоста не увидит
и отрапортует чистое восстановление после креша (D-083).

## 6. Восстановление после креша

Демон стартует и выполняет процедуру `recover()` для каждой незавершённой задачи. Весь проход —
одна функция [`startup::recover_task`], а не набор вызовов в `serve`: все ошибки здесь —
ошибки порядка, и порядок, размазанный по вызывающему коду, будет воспроизведён неправильно
во втором вызывающем (D-084).

**Задача, которая не начиналась, не восстанавливается.** Признак «началась» — запись внутри
попытки (`subtask`/`attempt` не пусты), то есть та форма, которую пишет раннер. Журнал из одних
книжных записей (`task_created`, прошлый `daemon_started`, усечение хвоста) — это задача без
первого шага; восстановление добавило бы ей `daemon_started` и попросило бы git пересоздать
ветку, которой нет, при каждом старте демона.

1. **Прочитать журнал** до конца. Если последняя строка обрезана — отбросить её (это
   гарантированно недописанная запись, потому что запись атомарна), записать событие
   `journal_truncated_tail` с числом байт.
2. **Проверить цепочку `prev`**. Разрыв — не пытаться «чинить» молча: задача → `blocked`
   с причиной `journal_corrupt`, эскалация человеку. Блок фиксируется **вне** журнала —
   в `panic.json` каталога состояния задачи и в очереди эскалаций (D-082): журнал со
   сломанной цепочкой нельзя даже открыть на запись, а «дописать после разрыва» сделало бы
   разрыв необратимым и стёрло бы улику.
   **Строка, которая прочиталась целиком, но не разобралась, — это не оборванный хвост**:
   `ReadOutcome` в этом случае нет вовсе (читатель возвращает `Err`), списка проблем тоже, и
   блокировка ставится прямо по пути ошибки, а не пробросом (D-084).
3. **Найти незакрытые tool-call'ы**: `intent`/`started` без `completed`/`failed`.
   - `Idempotent` → перезапустить;
   - `ByContent` → выполнить `probe`; результат записать как `effect_verified` /
     `effect_absent` и подложить модели как observation;
   - `Unknown` → L3 (откат к чекпоинту и новая попытка).
4. **Проверить worktree**: существует ли, на каком SHA, есть ли незакоммиченные изменения.
   Если worktree потерян — пересоздать из `agent/<task>`; если ветки нет — из базовой ветки
   и `checkpoint_created` последнего чекпоинта. Пересоздание адресуется **репозиторию**, а не
   потерянному worktree: `WorktreeManager` на удалённом каталоге ищет
   `<удалённый>/../<удалённый>-agent` и не создаёт ничего (D-084). Перед `worktree add`
   выполняется `worktree prune`: каталог, пропавший вместе с регистрацией в
   `.git/worktrees/`, — это ровно тот след, который оставляет креш, и без prune git отвечает
   «missing but already registered».
5. **Найти незавершённый откат L3**: `checkpoint_created {role:"rollback"}` без
   последующего `attempt_restarted` для той же `(subtask, attempt)`. Такой SHA ставится
   первым в список откатов (он описывает решение, уже принятое раннером, а не догадку о
   незакрытом вызове), а попытка закрывается `AbandonAttempt`. Маркер без `sha` — не
   доказательство откатa: сбрасывать дерево «в никуда» нельзя.
6. **Сверить состояние подзадач** с файлами: `attempts.json`/`subtasks.json` vs журнал.
   Победитель — журнал, расхождение перезаписывает **оба** файла из журнала (D-083).
   Отсутствующий или битый кэш читается как пустой: у производного файла нет права вето.
7. **Записать** `daemon_recovered` с описанием, что именно пришлось чинить. Не для
   заблокированной задачи: шаг писал бы в журнал, который только что признан нечитаемым.
8. Продолжить с места остановки: следующая подзадача или новая попытка текущей.
   Возобновление берёт у журнала последнее `task_state` и читает из него, где прогон
   остановился. Две вещи оно приводит в порядок до первого шага, потому что `kill -9` живёт
   ровно в этих зазорах (D-091):
   - **Брошенная попытка.** Недоступный бэкенд закрывает попытку `Abandon`, а не `Fail`:
     модель ничего не сказала о работе, и тратить на это бюджет подзадачи нельзя. Подзадача
     после этого снова `pending`, а не `running` — иначе `next_ready`, который предлагает
     только `pending`, не нашёл бы работы и цикл встал бы в `Stuck`.
   - **Подзадача, оставшаяся `running` в дереве.** Процесс, убитый между записью `running` в
     `TASKS.json` и чем угодно ещё, оставляет подзадачу, за которой нет работника. Слот
     прогона в этом процессе доказывает, что владелец — он, поэтому дерево переводится в
     `pending` до первого планирования; иначе тот же `Stuck`.

В журнал эти два шага пишутся по общему правилу: сначала дерево, потом запись.

Sink журнала (`journal::Sink`) вызывается **после** `sync_data` и обновления цепочки, поэтому
`attach` не покажет строку, которой нет в файле, и не покажет её раньше, чем её можно
найти после краха. `serve` создаёт один `Events` на демон и раздаёт его и обработчику
`start`, и `attach`: два разных вещателя дали бы двум клиентам разные потоки.

Всё это покрыто тестами-симуляторами с инъекцией падения в каждой точке протокола
(между `intent` и `started`, между `started` и `completed`, во время записи журнала,
во время `git commit`).

## 7. Бэкенд недоступен

Раздел честно делится на две части: что подключено к демону и что пока только реализовано в
`core`/`llm` и ждёт вызова. Второе — не обещание, а задел: у каждого пункта есть код и тест,
но продюсера в демоне нет.

**Работает сегодня.**

- Ошибки инференса классифицируются: `retryable` (таймаут, 429, 5xx, обрыв стрима) против
  `fatal` (400 на схему/невалидный запрос) — `llm::failure`.
- `400..=499` кроме `408` и `429` — `fatal` (запрос неверен); `408`/`429` и весь `500..=599` —
  `retryable`. Проверено на живом бэкенде: `502` может прийти после 300 с prefill на промпте
  130K — это не `fatal`.
- `Failure::is_retryable()` ложно для `ModelFault` (D-047): повтор усечённого ответа — это
  **другой** запрос (другой `max_tokens`), и решать должен вызывающий, а не формат ошибки.
- Любой сбой модели на шаге кончает попытку исходом `Ending::Backend { … }` →
  `AttemptTrigger::Abandon`: бюджет попыток не тратится (D-027), задача остаётся `running`,
  цикл пишет `backend_unavailable` один раз на непрерывный простой.
- `backend_unavailable` без последующего `backend_restored` даёт `Hold::WaitingBackend`
  в `scheduling` — `status` показывает причину простоя, а не «нет задач». Закрытая подзадача
  (`done`) — доказательство, что бэкенд ответил, и пишет `backend_restored`.
- Начало интервала читается из журнала (`backend::since_from_journal`), поэтому `kill -9`
  не перезапускает отсчёт.
- Повтор — человеческое действие: `immortality start --task <id>` продолжает с того
  состояния, которое назвал журнал. Демон сам задачу не перезапускает.

**Реализовано, но в демоне не вызывается.**

- Health-check: `Backend::health()` (один токен, а не `GET /models` — проверяет весь конвейер)
  и `backend::health_interval_secs` в конфиге существуют, но ни один цикл их не зовёт.
  Сегодня про недоступность узнают из ошибки запроса.
- Backoff `1s → 2s → 4s … max 60s`, до 6 попыток (`llm::failure::{backoff, should_retry,
  MAX_ATTEMPTS}`): политика описана и покрыта тестом, который проходит расписание вручную
  (`testkit/tests/client.rs`). Цикл в демоне её не применяет — `Model::complete` возвращает
  `String`, а `Backend::turn` делает ровно одну попытку (D-046: журнал должен видеть разрыв
  между попытками).
- Эскалация через 15 минут непрерывного простоя: `backend::while_unavailable` и
  `backend::escalation` готовы, `unavailable_escalate_after_secs` есть в конфиге, вызовов в
  проде нет.
- Офлайн-работа: `Queue::next_for_offline` и `Candidate::ineligible_for_offline` (D-087)
  реализованы и протестированы, но демон зовёт только `next_for_inference` — и только из
  `status`, чтобы объяснить простой. Отдельного диспетчера, который бы брал офлайн-работу,
  пока модель недоступна, в v0.1 нет.

**Следствие.** Пока бэкенд лежит, задача стоит: `start --task` после восстановления — это
то, что описано в §6, и оно работает. Автоматического продолжения «само поднимется» в v0.1
нет, и документация не должна его обещать.

## 8. Рост данных

- Сегменты журнала не удаляются никогда: компактный, основной аудит-след. Первый сегмент
  называется `JOURNAL.jsonl`, после ротации рядом появляются `JOURNAL.<stamp>.jsonl`; читатель
  принимает обе формы и склеивает их по метке времени.
- Тяжёлые тела (вывод инструментов, тела ответов модели) — в `artifacts/<sha256>`,
  дедуплицируются, TTL 30 дней (`storage.artifact_ttl_days`), чистятся `immortality gc`.
- Логи: текущий месяц — plain, по наступлении нового месяца предыдущий сжимается в
  `logs/YYYY-MM.log.gz`. Ретенция архивов — 12 месяцев (`storage.log_retention_months`).
  Оба слоя ведёт `core::logging` и `gc::collect`.
- `gc` отказывается удалять артефакты, на которые ссылается журнал незавершённой задачи
  (`gc::live_set`), и отказывается работать, если журнал задачи не читается: пустой набор
  живых артефактов — это разрешение удалить всё.
- **Транскриптов нет.** `StatePaths::transcripts_dir` — зарезервированный путь, его не
  пишет ни один код. Шаг модели и ответ лежат в `artifacts/`, метаданные — в
  `model_response`.
- **Диск-гард не подключён к демону.** `gc::disk_state` (1 GiB — предупреждение,
  256 MiB — `Hold::PausedDisk`) и `gc::hold_for_io_error` (`ENOSPC`/`EDQUOT`) реализованы и
  покрыты тестами, но продюсера в раннере нет: `Hold::PausedDisk` не выставляется ниоткуда,
  а свободное место смотрит только `immortality doctor` (пороги 2 GiB / 512 MiB — его
  собственные, для человека). Сегодня единственный признак переполнения — упавшая запись;
  задача при этом не встаёт на `paused_disk`, а кончается ошибкой. Молча продолжать нельзя,
  и это записано здесь, чтобы расхождение было видно, а не выяснялось на ENOSPC.
