# План работ и критерии готовности

Каждая веха заканчивается работающим состоянием и тестами. Порядок выбран так, чтобы
самые дорогие ошибки (состояние, восстановление, протокол инструментов) были пойманы до
того, как появится UI и агентная петля.

## Про оценки

- Единица — **фокусированный день** одного разработчика: без встреч, переключений и ревью.
  Календарь при частичной занятости — умножать на 1.4–1.6.
- Оценка включает тесты, без которых шаг не считается сделанным.
- Оценка **не включает** отладку на живой модели: на локальных моделях это отдельный,
  плохо предсказуемый вид работы. Он вынесен в S1 и M6.
- Оценки по незнакомым API (`launchd`, `git stash create`, `portable-pty`) даны с
  запасом ~30%.

| M1.2 ✅ | Журнал: JSONL, атомарная запись (temp + fsync + rename), сегменты по 8 MiB, монотонный `seq`, цепочка `prev`, чтение с обрезкой битого хвоста | обрыв записи на каждом байте; разрыв цепочки; конкурентная запись из двух потоков; повторное открытие сегмента | 2.5 |

| M1.5 ✅ | Чекпоинты: скрытые (временная ветка / `stash create`) и содержательные; откат `read-tree --reset -u` с предварительным снимком незакоммиченного (D-134) | откат возвращает точное дерево; незакоммиченные правки не теряются; откат не двигает ветку `agent/<task>`; откат к несуществующему SHA → ошибка | 1.5 |

**Почему M1.8 большой:** это актив, на котором держатся все остальные тесты проекта.
Без него «0 потерянных данных при `kill -9`» проверить нечем.

**Критерий вехи выполнен.** `testkit::sim` проигрывает реальный tool-call через реальный
журнал и умирает в каждой из семи точек (`BeforeIntent`, `AfterIntent`, `BeforeStarted`,

классов идемпотентности и каждого из трёх ответов `probe` — 63 комбинации. Каждая
проверяет: у каждого незакрытого вызова ровно одно решение; обрезанный хвост снимается
первым; вызов с неизвестным эффектом не повторяется; запись о восстановлении идёт
последней.

**Риск:** самый высокий в проекте. Атомарность + восстановление — источник тонких багов.
Правило: ни один шаг M1 не считается сделанным без теста с инъекцией сбоя.

## M2 — LLM-слой (10 дней, **выполнено**)

**Сделано, когда:** mock-сервер отдаёт все сценарии деградации, и клиент выходит из
каждого предсказуемым состоянием.

> Факты с живого бэкенда (см. `backend-check-swift-iq2xs.md`): нативный tool-calling
> работает, аргументы в стриме приходят посимвольно, в потоке есть `: keep-alive`,
> reasoning идёт отдельным полем и отключается через `chat_template_kwargs`. Это
> сокращает объём fallback-парсера: он нужен как страховка, а не как основной путь.

| Шаг | Что делаем | Тесты | Дней |
| --- | --- | --- | --- |
| M2.1 ✅ | Типы запроса/ответа OpenAI, non-streaming путь, сериализация | serde round-trip; запрос совпадает с эталонным JSON | 1 |
| M2.2 ✅ | SSE-стриминг: дельта-ассемблинг контента и `tool_calls` по индексам, склейка частичных аргументов | ответ, разрезанный на 1-байтные чанки; два tool-call в одном ответе; пустой `delta` | 2 |
| M2.3 ✅ | Классификация ошибок (`retryable`/`fatal`), backoff 1→60 с, health-check, отмена запроса | 429/5xx/таймаут/обрыв стрима; отмена посреди стрима не оставляет висящих задач | 1.5 |
| M2.4 ✅ | Извлечение вызовов: нативный путь → fallback (```json, XML-теги, «почти-JSON» с починкой). Нативный путь подтверждён на живом бэкенде; fallback — страховка | матрица из ~20 деградаций (по данным S1); починка не «додумывает» аргументы | 1.5 |
| M2.5 ✅ | Валидация аргументов по JSON Schema, рендер ошибки для модели с ожидаемой схемой | пропущенное обязательное поле; лишнее поле; неверный тип | 1 |
| M2.6 ✅ | Учёт токенов: `usage`, эвристика как fallback, калибровка по истории | ответ без `usage`; расхождение эвристики и usage < 15% после калибровки | 0.5 |
| M2.7 ✅ | Mock-сервер в `testkit`: сценарные ответы из файла, стриминг, задержки, ошибки, «модель зациклилась» | сам mock-сервер: детерминизм, воспроизводимость, остановка без утечек | 2.5 |

**Критерий вехи выполнен.** Mock-сервер отдаёт все сценарии деградации — 429 с
`Retry-After`, 5xx, обрыв посреди стрима, оборванный tool-call, in-band ошибку в 200,
молчащий бэкенд, зацикленную модель — и клиент выходит из каждого предсказуемым
состоянием. Три падения на этих тестах были настоящими багами клиента и исправлены:
дефолтный `finish_reason` скрывал обрыв посреди ответа, отмена работала по транспортному
чанку вместо SSE-payload, и `usage` без `cache_n` считался отсутствующим.

**Риск был M2.4** — fallback-парсер легко превращается в генератор ложных вызовов.
Правило выдержано: любая починка только нормализует синтаксис и никогда не добавляет
отсутствующие поля; невосстановимый вызов становится observation модели, а не догадкой.

- **Лимит шагов съедает готовую работу.** Первая попытка нашла правку, гейт `GATE_EXIT=0`,

  `evaluate_gates` вызывается только из `settle_claim`, поэтому при `Ending::Steps` гейты не
  проверяются вообще, а `restart::decide` превращает исчерпание бюджета в откат найденного.

**Реализовано, но не подключено к демону.** Ещё один класс расхождений, найденный при аудите
документации перед `v0.1.1`: механика есть, тесты зелёные, продюсера в прогоне нет. Это не
скрытый дефект — каждый прогон ведёт себя так, как описано в `docs/state-and-recovery.md` §7–8,
но метки ✅ выше читаются шире, чем есть. Список, чтобы не выяснять это заново:

## 0.2 — петля не теряет найденное

**Сделано, когда:** `immortality metrics --json` на живом прогоне даёт одновременно
`green_attempts_not_closed == 0`, `step_exhaustions_without_gates == 0` и `closed_green >= 5`, а
`settled_after_step_budget > 0` — то есть хотя бы одна подзадача закрылась гейтами после
исчерпанного бюджета шагов, а не заявкой. Три числа, а не одно: они отвечают на три разных
вопроса, и «ноль потерянного» без «ноль непроверенного» и без «путь D-115 хотя бы раз исполнился»
берётся прогоном, который ничего не нашёл.

Числа берутся с прогона, где модель действительно работает; планка `closed_green >= 5` — с
`black_jack`, потому что это записанный прогон, ради которого веха заведена. Позже она проверяется
тем же `metrics` на любом живом прогоне с достаточным числом подзадач.

**Почему формулировка изменилась.** Исходная — «нет попытки, где `gate_result` с
`gate: "verdict"`, `passed: true`, а подзадача закрылась не как `done`» — на записанных журналах
выполнялась **до** начала работ вехи, включая третий прогон, ради которого веха и заведена. Причина
пустоты: до D-115 гейты вызывались только из `settle_claim`, поэтому попытка, нашедшая правку и
исчерпавшая шаги, писала `attempt_failed { ending: "steps" }` и **не писала `gate_result` вовсе**.
Критерий «нет зелёной попытки, которая не закрылась» был истинен ровно потому, что зелёной записи
не существовало. Замер по трём журналам: `green_attempts_not_closed = 0` во всех трёх при
`step_exhaustions_without_gates = 2, 1, 2`.

Поэтому критерий разложен на то, что он на самом деле проверяет: «гейт сказал да, а закрытия нет»
(`green_attempts_not_closed`), «гейт не спрашивали» (`step_exhaustions_without_gates`) и «новый путь
исполнился» (`settled_after_step_budget`). Все три считает `core::metrics`, все три печатает
`immortality metrics` словами, а не только числом.

Планка `closed_green >= 5`, а не `6`, потому что шестая подзадача (`verify_shuffle_spec`) в
записанной форме невыполнима: `Kernel#rand` при `Array#shuffle!` работает на внутреннем RNG, и
подменить его, не переписав спеку, нельзя. Требовать `6` значило бы требовать, чтобы гейт с ложным
`DoD` позеленел. Если `DoD` будет переписан на наблюдаемый контракт, планка поднимется до `6` — но
это правка плана, а не вехи.

**Чего критерий не доказывает.** `green_attempts_not_closed == 0` на журнале, где
`step_exhaustions_without_gates > 0`, ничего не говорит о потере работы: там гейты просто не
спрашивались. Именно поэтому третье число обязательно, а `metrics` при ненулевом
`step_exhaustions_without_gates` печатает, что журнал предшествует D-115 и о потере работы
молчит.

Порядок внутри вехи: сначала потеря работы, потом поверхность.

**1. Бюджет шагов не обрывает готовую работу. ✅ (D-115).** `evaluate_gates` вызывался только из
`settle_claim`, поэтому при `Ending::Steps` гейты не проверялись вообще, а `restart::decide`
превращает исчерпание бюджета в откат найденного. Теперь на исчерпании **бюджета шагов** гейты
спрашиваются один раз: зелёные → попытка `Succeeded` и `Ended::Verified`, красные → обычный откат.
Пустой дифф не закрывает ничего — иначе `DoD` с одним ревью закрывал бы подзадачу, над которой
ничего не сделано (D-115). Токены и время гейты не спрашивают: там неизвестно, хватило бы бюджета
на оставшиеся проверки.

**2. D3 видит длительности (D-109). ✅** Узкий нормализатор digest'а: только измеренные формы
`0.04258 seconds` и `[exited 0 in 0.3 s, …]`. Общая нормализация чисел остаётся отвергнутой
(D-104, D-108), а наблюдение модели остаётся сырым — нормализуется digest, а не вывод.

**3. `DoD`-проверка не может быть пайпом (D-116). ✅** `/bin/sh` отдаёт пайпу код возврата
последней команды, поэтому `cargo test 2>&1 | tail -20` зеленеет на несобранном коде. Замер по
журналам dogfood: одиннадцать таких наблюдений (пять в `word-count-fresh`, шесть в `word-count`),
в каждом `error[E…]` в выводе и `[exited 0 …]` в сводке. `Dod::validate` теперь отклоняет
проверку с неэкранированным `|` — на загрузке плана и на сплите. `||` и пайп внутри кавычек
(`grep -qE 'a|b'`) остаются законными; `set -o pipefail` отвергнут, потому что его нет в
`/bin/sh` (проверено на `dash`).

**Снято с вехи: сброс серии D6 по зелёной проверке.** Пункт собирался вызывать
`Signals::record_progress` (`detect/mod.rs:373`) на зелёном гейте, но `Signals` — поле
`StepLoop` (`runner.rs:1363`, создаётся `runner.rs:1402`) и умирает с попыткой, а `settle_claim`
(`runner.rs:683`) вызывается после возврата `drive` (`runner.rs:594`) и `Signals` не видит.
Замер по трём журналам dogfood показал, что правка была бы неотличима от её отсутствия: максимум
**2** правки одного файла подряд при пороге **6**, и та единственная «зелёная» проверка внутри
серии оказалась ложной по причине из пункта 3. `record_progress` остаётся публичным API без
вызова — долгом он больше не числится.

**4. Судья (D-111). ✅** Модельная проверка команды **до** запуска, только для `Effect::External` с
причиной «незнакомая программа»; три исхода, при сбое — `escalate`. Кэш вердиктов в журнале, по
сигнатуре плюс отпечатку политики, без сброса на попытке. В журнал пишется отдельным видом
записи: иначе при разборе живого прогона не отличить его вызовы от вызовов модели.

**4a. Структурная причина `External`. ✅** `Classification.source: Option<External>` — семь
вариантов по числу способов дойти до вердикта; судье разрешён ровно `UnknownProgram`
(`External::is_a_question`). `reason` остаётся прозой для модели: у полей разные читатели, и
склеивать их значило бы вернуть привязку к тексту. Два инварианта закреплены тестами: любой
`External` несёт `source`, и вопросом считается только незнакомая программа — `git push`, `curl`,
`perl -e`, `$CMD` и незакрытый `$(` им не являются.

**4b. Судья: трейт, разбор, вызов. ✅** `tools::judge` — `Judge`, `Judgement`, фиксированный
`SYSTEM`, `prompt`, `parse_reply` (закрыт по умолчанию: проза и `deny` без причины — ошибка).
`PolicyGate::with_judge`/`set_judge` заполняет слот; вызов стоит внутри ветки эскалации, поэтому
`yolo` и доверенный хост отключают судью по построению. `Allow` не отменяет проверку путей.

**4c. Кэш вердиктов и проводка. ✅** Ключ — сигнатура команды (программа плюс форма аргументов,
значения → placeholder) и отпечаток политики (`yolo`, `deny_programs`, `deny_write_globs`,
`trusted_hosts`). Хранится **только `allow`**: `deny` и `escalate` — ответы, которые изменившийся
мир может сделать неверными, и узнать об этом стоит реального шага. Вердикты пишутся в журнал
отдельным видом записи `judge_verdict` (схема `v: 2`, читатель принимает `v <= SCHEMA_VERSION`) и
читаются назад при старте, поэтому `kill -9` не заставляет платить заново. Заполнение слота —
`ToolsetDeps::with_judge` перед `toolset::build`: судье нужна модель, модели нужен гейт, а
`Recorded` собирается в `start.rs`, где обе уже есть. Дренаж вердиктов делает раннер в
`flush_judgements` **после** `drop(log)`, потому что `run_tool` держит `&mut Journal` и журнал
single-writer. Проверено на прод-пути: `an_unknown_program_is_decided_by_the_judge_on_the_production_path`.

**5. `delegate`. ✅** Цикл разорван слотом: `SubAgentSlot` (`RwLock<Arc<dyn SubAgent>>`) живёт в
`ToolsetDeps::sub_agent` как `Arc`, `toolset::build` собирает `Delegate::deferred` над ним, а
`start::execute` заполняет слот **после** того, как `Runner` построен над тем же `Registry` —
`crates/daemon/src/sub_agent.rs::install` через `wire_delegation`. `RwLock`, а не `OnceLock`: вторая
установка должна заменять, а не молча ничего не делать, иначе повторный прогон делегировал бы
первому раннеру. Слот стартует с `NoSubAgent`, который отказывает, — сборка, забывшая установку,
получает ошибку с подсказкой, а не успешный пустой отчёт.

`BriefRunner` — это настоящий `SubAgent`: он берёт у родителя модель, реестр, гейт, артефакты и
счётчик, а отличает только лимит шагов из вызова, `gates: Some(BriefGates)` и
`delegation_depth: 1`. Свой журнал субагент пишет в `delegations/<del_id>/` рядом с отчётом:
`Journal` single-writer, и родитель держит свой писатель на весь вызов, поэтому общий сегмент
сломал бы цепочку digest. Отсюда же единица восстановления: `delegate` — один вызов, а не шаги
субагента, и проба смотрит на отчёт.

`BriefGates` — пустой мир гейтов намеренно: `gates: None` означал бы «проверить нечем» и **валил
бы** каждый claim с сообщением про ошибку проводки (первый прогон теста это и показал). Пустой
`Diff` и пустой `DoD` дают `Passed` без обращения к миру, а `Finish::Done` значит ровно «бриф
сказал, что закончил»; работу судит `DoD` родителя на том же worktree.

Вложенность запрещена не вторым реестром, а глубиной: `Runner::delegation_depth` штампуется в
`ToolCtx::with_depth`, и `refuse_nested` отвергает при `depth != 0`. Без этого субагент делил бы
реестр родителя и его `delegate` выглядел бы как вызов верхнего уровня — рекурсия до исчерпания
бюджетов. Проверено на прод-пути:
`a_delegated_brief_gets_its_own_journal_and_cannot_delegate_onward` (слот заполнен, свой журнал,
вложенность отвергнута, шаги субагента не попали в журнал задачи) и
`a_brief_that_spends_its_steps_is_reported_as_exhausted_not_done` (исчерпание ≠ `done`, гейтов
бриф не гоняет). Пять саботажей: слот не заполняется, журнал пишется в каталог родителя, глубина
не штампуется, `Done` выдаётся за любое окончание, бриф наследует гейт-мир родителя. Пятый сначала
не ловился — пришлось проверять отсутствие `gate_result` в журнале брифа.

**6. Linux — поддерживаемая платформа (D-110). ✅** `service.rs` разделён на
`service/{mod,launchd,systemd}.rs`: общее (`LABEL`, `RESTART_SECONDS`, `SUBCOMMAND`, `MANAGER`,
`ServiceSpec`, `Status`, `Installed`) и два бэкенда. Юнит `systemd --user` пишется в
`$XDG_CONFIG_HOME/systemd/user/`, включается симлинком в `default.target.wants` (абсолютным:
относительный systemd ищет внутри wants-каталога и получает висячую ссылку), поднимается через
`daemon-reload` и `restart`. `Restart=on-failure`, а не `always`: чистый выход — это
сознательная остановка. Пути: `$XDG_STATE_HOME/immortality` для состояния и
`$XDG_CONFIG_HOME/immortality` для конфига, раздельно намеренно — `0700` на состоянии осмыслен
только когда читаемый конфиг лежит в другом месте. На macOS пути не меняются, миграции нет.

Оба бэкенда компилируются на любой платформе, `pub use` выбирает один: генерация юнита и
последовательность вызовов `systemctl` проверяемы на macOS подменённым скриптом, и `cfg` на
модуле означал бы, что эти тесты существуют только в CI. Настоящие `plutil` и `launchctl`
остаются под `cfg(target_os = "macos")`; `systemctl`-тесты намеренно не ограничены платформой.
JSON-поле `plist` в `service install/status` сохранено как алиас к `unit`, чтобы скрипты
`0.1.2` не сломались на смене названия.

Две поломки Linux-сборки, найденные при этом и невидимые на macOS по построению (обе
компилируются только там, где `cfg` уходит в другую ветку):

| Что | Почему macOS не видел |
| --- | --- |
| `paths::home()` под `cfg(any(target_os = "macos", test))`, а зовёт его `xdg()` в Linux-ветке | на macOS `home()` нужен самому `data_dir()`, и `test` его тоже включает — функция есть всегда |
| `tests/service_agent.rs` импортировал `Agent`/`plist` через `pub use`, который на Linux указывает на `systemd` | файл не был под `cfg`, но звал macOS-имена |

Первое — настоящая ошибка компиляции Linux-релиза; второе сломало бы `cargo test` в Linux-джобе.
Оба стоят одной строки каждый и стоят того, чтобы быть записанными: `cfg` на экспорте — это
`cfg`-ошибка, которую видит только тот, кто собирает на другой платформе.

**7. `0700` на каталоге состояния. ✅** Сейчас `0600` получают только сокет и токен, а сам
каталог `~/Library/Application Support/immortality` создавался с умалкой (`0755` на типичной
macOS-машине), то есть токен и артефакты журналов читал любой локальный аккаунт.
`core::paths::create_private_dir` создаёт недостающее и ставит `0700`; `bind` использует её для
родителя сокета. Правило узкое намеренно: режим ставится **только** на каталог, созданный этим
вызовом. Существующий каталог сохраняет свои права — миграции нет (D-110 про Linux-паритет,
здесь то же соображение), и молчаливое ужесточение прав на каталоге, который пользователь мог
сделать общим, — сюрприз, а не защита.

**8. Работа закрытой подзадачи попадает в ветку задачи. ✅ (D-122).** Замыкание цикла не
коммитило ничего: `agent/<task>` оставался на базовом коммите, работа лежала только в worktree, а
`merge` отчитывался `merged` (см. пункт 9). Замер по трём прогонам: `agent/<task>` совпадает с
`main`, работа существует как незакоммиченные изменения и в `agent-ckpt/<task>`. Теперь
`Pass::commit` на `Stop::Done` (до записи `done`) кладёт дерево на ветку через
`commit_to_branch` — `add --all` → `write-tree` → `commit-tree` → `update-ref`, без чекаута, —
одним Conventional Commit на подзадачу. Первая попытка использовала `commit_with_trailers`, и
`git checkout --force` ветки, на которой worktree уже стоит, **откатывал все tracked-правки**:
измерено, и это стирало работу подзадачи прямо перед task-level гейтом.

**9. `merge` приземляет работу и не врёт об этом. ✅ (D-121).** Два дефекта одного стража.
Первый: «главный чекаут чист» считал грязью `.agent/PLAN.md`, `.agent/TASKS.json` и
`.agent/JOURNAL.jsonl`, которые пишет сам демон, поэтому `merge` отказывал на нормальном исходе
успешной задачи; фикстура прятала это, держа `.agent/` в `.gitignore`. Второй: ветка без коммитов
впереди `HEAD` сливается успешным no-op («Already up to date»), и старый код писал `merged` для
работы, которой в ветке нет. Теперь `.agent` исключён из стража (`:(exclude).agent`, отказ
называет конкретные файлы), а `rev-list --count HEAD..agent/<task> == "0"` — отказ, называющий
`agent-ckpt/<task>`.

**10. Task-level гейт диффит от точки ветвления задачи. ✅ (D-123).** Регрессия, которую породил
пункт 8: ревью диффило против `HEAD` и видел всю работу, пока та была незакоммичена; коммит
перенёс её в `HEAD`, и дифф стал пустым. Замерено на живом `word-count`: три подзадачи зелёные,

`gates::task_base` даёт `merge-base` между `HEAD` репозитория и `agent/<task>`, и он же — база
`RealGates::base` на прод-пути. Ревьюер, одобряющий пустой дифф, не одобряет ничего.

**11. `status` не называет идущую задачу пустой. ✅ (D-120).** Во время первой попытки
`tsk_01M7HJEFXD7YDHGM59Y4X57FTZ` `status` печатал «1 with no subtask left to run», а
`scheduling.next` был `null`. `has_work` — это `next_ready`, а тот предлагает только `pending`
подзадачи, поэтому дерево с одной `running` подзадачей читалось как пустое. Добавлены
`Candidate::in_flight` и `Ineligible::InFlight`: `has_work` остаётся `false` (второй попытке на
том же дереве нельзя начинаться), но причина называет работу, а не её отсутствие.

**Вне критерия, найдено и закрыто по ходу: проектный конфиг (D-119).** `serve` читает конфиг один
раз и ищет проектный слой от cwd процесса, а под launchd это `/` — поэтому
`<repo>/.agent/config.toml` не применялся никогда, и трёхслойный порядок из `docs/design.md` §3

не входит, но без этого живой прогон шёл бы по чужой политике хранения.

## 0.3 — автономия доказуема

**Сделано, когда:** на живом журнале одновременно выполнены три условия: `escalations_total > 0`
(эскалация записана), `escalations_pending > 0` в момент, когда человек ещё не ответил
(эскалация ждёт), и попытка уведомления видна в журнале отдельной записью с исходом
(`osascript` запущен либо пропущен, с причиной).

Три условия, а не одно, потому что каждая пара из них ловила бы половину: `escalations_total > 0`
без `pending` — это запись о вопросе, который уже закрыт, то есть механизм писал в журнал сам
себе; `pending` без уведомления — та же дыра, что сегодня («человек не знал»); уведомление без
записи недоказуемо. Сегодня `escalations_total` и `closed_with_escalation` всегда нули, и
`docs/metrics-v0.1.md` §«Что «без вмешательства» значит здесь» признаёт, что ноль означает
«событий в журнале нет», а не «эскалаций не было». Пока это так, заявление об автономности
держится только на `longest_green_streak` и `restarts`.

**Что придётся изменить в коде, а не только подключить.** `Notifier::notify` сегодня возвращает
`()` намеренно: «уведомление — вежливость поверх долговечной записи», и обрабатывать нечего
(`notify.rs:13-18`). Отсутствие возврата — верное решение для вызывающего, но оно делает
недоказуемым сам факт попытки: в журнале останутся только строки `debug`, которые в проде не
пишутся. Поэтому `notify` меняет контракт на исход (`Delivered` / `Skipped(reason)`) — не чтобы
вызывающий мог «обработать сбой», а чтобы веха имела наблюдаемое свидетельство. Это изменение
публичного трейта, и оно должно прийти вместе с записью в журнал, а не раньше.

**Чего этот критерий не доказывает.** Он говорит «попытка доставки была и записана», а не «человек
узнал»: `osascript` вернул успех означает, что программа запустилась и завершилась, а не что
уведомление показано. Проверять показ нечем, и притворяться, что проверяем, было бы хуже —
поэтому граница названа здесь, а не спрятана в формулировке «доходит до человека».

**1. Цикл с таймером.** `serve::run` (`cli/src/serve.rs`) делает recovery, биндит сокет и уходит
в `tokio::select!`; `tokio::time::interval` в `daemon` и `cli` нет. Без цикла некуда поставить
health-check, эскалацию по простою и диск-гард — три строки таблицы выше ждут именно его. Но
начинать с него стоит и по другой причине: уведомление и `JournalQueue` из пункта 2 включаются
не «когда готово», а когда есть событие, которое надо доставить.

**2. `JournalQueue` и `MacNotifier` — вместе. ✅ (D-117).** Журнал без уведомления: «эскалация
была, человек не знал». Уведомление без журнала: «человек знал, доказать нечем».

Сделано иначе, чем планировалось, потому что планировалось неверно. `JournalQueue` открывал
журнал на каждое изменение, а демон держит писатель задачи открытым весь прогон: второй писатель
даёт `seq=1` дважды и `corrupt=true`. Замерено пробой, а не выведено. Теперь очередь **собирает**
записи (`Pending`), а вычерпывает их тот, кто владеет `&mut Journal` — `Runner::flush_escalations`
рядом с `flush_judgements`, по тому же образцу, что уже применён к судье. `Escalate::collecting`
принимает `Arc<JournalQueue>`, чтобы инструмент и раннер держали один коллектор: два экземпляра на
один путь выглядят одинаково и молча теряют записи.

`notify::system()` выбирает `MacNotifier` на macOS и `Silent` на прочих, и `start::execute` ставит
его в `ToolsetDeps`. До этого прод ставил `Silent` и не звал `.notifying(...)` вовсе — `MacNotifier`
существовал только в тестах.

**Чего это не закрывает.** Ответ человека всё ещё не доходит до модели: `blocking_question` и
`answer_question` в проде не зовёт никто. Обещание `escalate` «the decision arrives as an
observation» остаётся невыполненным, и это следующий шаг, а не этот.

**3. `backoff`/`should_retry`** подключаются к `LlmModel::complete` (`runner.rs:249`), которая
сегодня делает одну попытку на шаг (D-046).

**4. `Plan::refresh`** — не сам по себе: `Pass` держит `&mut Plan`, а `history` читается один раз
(`cycle.rs:220`), поэтому обновлённый план исполнялся бы против старой истории.

**5. Компактация и `transcripts_dir` — одна дырка.** `Verdict::Compact` не обрабатывается
потому, что компактация «требует своего вызова модели и места, куда писать сводку»
(`runner.rs:1723-1725`); `Kind::Compaction` в журнале существует и не пишется никогда.

## 0.4 — масштаб

**Сделано, когда:** при `max_inference_concurrency = 2` интервалы двух задач **разных проектов**
пересекаются, а при `max_inference_concurrency = 1` — нет. Интервал читается из журнала как пара
записей одной попытки: `model_request` (момент `at`) до следующего `model_response`. Плюс `flock`
не даёт двум записям в один журнал перемешаться: попытка второй задачи завершается внятной
ошибкой, а не порчей файла.

Слот прогона на проект (D-142) закрывает этот класс **внутри одного демона**: вторая задача того
же проекта получает отказ до первой записи. `flock` остаётся нужен для второго демона на том же
репозитории — сейчас `daemon.lock` не даёт запустить второй демон на одном state root, но два
state root на один репозиторий никто не проверяет.

Оба значения, а не одно: сегодняшнее поведение — это «всегда параллельно, независимо от
настройки», поэтому проверка только на `2` не отличила бы работающий семафор от его отсутствия.
Дефолт `1` (`config.rs:221`) означает, что «работает как раньше» и «соблюдает настройку» — разные
утверждения, и веха обязана доказать второе.

Отдельно: `at` — это момент записи, а не длительность запроса, поэтому «перекрытие» определяется
только по паре `model_request`/`model_response` внутри одной попытки. Если в `2` окажется, что
записи пар чередуются, но интервалы не пересекаются, семафор работает, а тест не доказал
обратного — значит критерий читается как «интервалы пересеклись», и фикстура обязана сделать
запросы достаточно долгими, чтобы перекрытие было видно, а не выводилось из порядка строк.

`RunSlot` теперь держится на проект (D-142), поэтому две задачи одного проекта параллельно не
пойдут; две задачи **разных** проектов по-прежнему дают два параллельных запроса без всякого
семафора — слот защищает журнал, а не инференс. `Queue::new()` пересоздаётся на каждый `status`
(`server.rs:767`), поэтому ротация и `last_served` не переживают вызов. `Priority::High` не
выставляется никем: `scheduling.rs:66` жёстко ставит `Normal`. `Hold::PausedDisk` недостижим,
потому что `hold_for_io_error` не вызывается, а `Ineligible::Disk` — его читатель.

Порядок внутри вехи диктуется зависимостями: `flock` и `Priority` бессмысленны без
диспетчера, который держит очередь дольше одного вызова; диск-гард бессмыслен без продюсера,
который выставляет `Hold::PausedDisk`.
