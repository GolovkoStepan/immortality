# Архитектура

## 1. Форма системы

```
┌─────────────────────────────────────────────────────────────┐
│  immortality serve  (демон, один на пользователя)           │
│                                                             │
│  ┌────────────┐  ┌───────────┐  ┌───────────────┐           │
│  │ Scheduler  │→ │  Runner   │→ │  Tool layer   │           │
│  │ (очередь   │  │ (агентный │  │ policy/exec/  │           │
│  │  задач)    │  │  цикл)    │  │ worktree/shell│           │
│  └────────────┘  └─────┬─────┘  └──────┬────────┘           │
│         │              │               │                    │
│         ▼              ▼               ▼                    │
│  ┌────────────────────────────────────────────┐             │
│  │ immortality-core: состояние, журнал,       │             │
│  │ дерево задач, детекторы, бюджеты, recovery │             │
│  └────────────────────────────────────────────┘             │
│         │                                                   │
│  ┌──────▼───────┐   unix-сокет (построчный JSON + events)   │
│  │ LLM client   │◄──────────────────────────────────┐       │
│  └──────┬───────┘                                   │       │
└─────────┼───────────────────────────────────────────┼───────┘
          │ HTTP /v1 (OpenAI)                         │
          ▼                                           │
   llm-server:47832                    immortality CLI (attach/status/...)
```

Демон — единственный владелец состояния и единственный, кто говорит с моделью.
Клиент можно убивать, перезапускать, открывать несколько — он лишь подписчик событий и
отправитель команд. Именно это даёт «работа идёт днями, что бы ни случилось с терминалом».

Протокол — построчный JSON, не JSON-RPC 2.0 (D-069): одна строка — один запрос, одна
строка — один ответ, `rpc::VERSION` в `hello`. Методы закрыты списком
(`hello`, `status`, `escalations`, `approve`, `attach`, `plan`, `log`, `metrics`, `gc`,
`merge`, `start`). `hello` — единственный метод, отвечаемый до сверки токена, потому что он и есть
сверка. `MAX_LINE_BYTES` = 1 МиБ, и ограничение действует при чтении, а не после: иначе
клиент заставляет демон аллоцировать без предела.

`attach` отдаёт бэклог внутри подтверждения и только потом начинает стрим, поэтому клиент,
подключившийся посреди прогона, не делает второй круг за историей. Границы между бэклогом
и стримом нет только при одном условии: подписка создаётся до чтения журнала и стрим
отбрасывает всё до `next_seq` из подтверждения. Потерять запись нельзя, дубликат — можно,
и он снимается водяным знаком; обратное (не потерять дубликат, но потерять запись) не
лечится ничем.

Живой прогон питает этот стрим через `journal::Sink`: `Journal::append` зовёт sink **после**
`sync_data` и обновления цепочки, поэтому подписчик никогда не увидит запись, которой нет в
файле. Sink получает один `Events` на демон (D-091), а не отдельный на обработчик, иначе
`attach`, открытый до `start`, не увидел бы прогон.

`start` — один метод с двумя формами: `goal` заводит новую задачу (при отсутствии плана он
сначала строится планировщиком), `task` возобновляет существующую с того состояния, которое
назвал журнал. Запуск идёт на отдельном std-потоке, потому что `LlmModel` владеет
current-thread runtime и паникует при drop в async-контексте. Второй `start` той же задачи в
одном процессе — отказ: журнал однописательный, и две цепочки — единственное
неисправимое состояние этой архитектуры.

`status`, `escalations` и `attach` фильтруют записи по `task`: `JOURNAL.jsonl` один на
репозиторий, а `seq` в нём сквозной, поэтому фильтр — обязанность каждого читателя, а не
свойство ридера (D-070).

## 2. Крейты

| Крейт | Ответственность | Зависимости, которых быть не должно |
| --- | --- | --- |
| `immortality-core` | Типы домена, дерево задач, машина состояний, журнал, чекпоинты, бюджеты, детекторы зацикливания, сборка контекста | `tokio`, `reqwest`, `hyper`, `immortality-tools`, `immortality-daemon` — ядро чистое и синхронное; проверяется отдельным джобом CI |
| `immortality-llm` | HTTP-клиент OpenAI-совместимого API, стриминг, парсер и починка tool-call'ов, валидация по JSON Schema, учёт токенов, health/backoff | логика задач |
| `immortality-tools` | Исполнение инструментов, policy engine, worktree, `shell` (процесс на команду), реестр процессов, прогнозы эффектов (probe) | знания о планировщике |
| `immortality-daemon` | Планировщик, Runner (агентный цикл), RPC-сервер, интеграция с launchd и systemd, lifecycle | — |
| `immortality-cli` | `clap`-команды, подписка на события, рендер в стиле Claude Code | — |
| `immortality-testkit` | Mock OpenAI-сервер, симулятор точек краха, фикстуры, golden-хелперы (полный прогон-симулятор живёт в `daemon/tests`: testkit не может зависеть от демона) | — |

Правило направления зависимостей: `cli → daemon → tools → llm → core`. Обратных стрелок нет;
`core` не знает ни про один другой крейт.

Бинарь один: `immortality` с подкомандой `serve`. Это упрощает установку и симлинки.

```rust
rust-version = "1.99"
license = "MIT OR Apache-2.0"

[workspace.lints.rust]
warnings = "deny"
unsafe_code = "forbid"
```

## 3. Конфигурация

Приоритет (позже = сильнее): встроенные дефолты → глобальный конфиг → проектный конфиг →
env → CLI-флаги. Env-слой узкий, а не «любой ключ через `IMMORTALITY_*`»: читаются ровно
`IMMORTALITY_BASE_URL`, `IMMORTALITY_MODEL`, `IMMORTALITY_LOG_LEVEL`, `IMMORTALITY_YOLO`,
`IMMORTALITY_SOFT_BUDGET_TOKENS` и `IMMORTALITY_HARD_BUDGET_TOKENS`. Политик, кроме `yolo`,
в env нет намеренно: `IMMORTALITY_STATE_DIR` и `IMMORTALITY_GLOBAL_CONFIG` выбирают файлы,
а не права, и в эту лестницу не входят.

- **Глобальный** `~/Library/Application Support/immortality/config.toml` (Linux:
  `$XDG_CONFIG_HOME/immortality/config.toml`, D-110) — единственное место,
  где живут **политики безопасности**: `workspace_root`, `trusted_hosts`, `allow_write_globs`,
  `deny_write_globs`, `deny_read_globs`, `deny_programs`, `yolo` и пять флагов разрешений.
  Встроенный deny-список (`**/.git/**`, `**/.agent/config.toml`, `**/.agent/JOURNAL*`) не
  настраивается: это не политика, а форма журнала.
- **Проектный** `<repo>/.agent/config.toml` — те же секции, что в глобальном, кроме
  `[policy]`: профили моделей, бюджеты контекста, лимиты цикла, пороги детекторов, `[storage]`,
  `[logging]`. Может правиться агентом (через обычную правку файла в worktree), но **права не
  расширяет**: секция `[policy]` здесь игнорируется целиком и даёт предупреждение в
  `Loaded::warnings` (`tracing::warn`, не журнал). Промптов в конфиге нет: системный промпт
  собирает `daemon::start::system_prompt` из цели задачи.
- **Когда читается**: глобальный конфиг читается один раз при старте процесса (`serve`), и демон
  держит его до конца жизни. Правка любого файла конфига применяется перезапуском демона, а не
  посреди прогона — это и есть защита от того, что правила меняются под руками у идущей задачи.
  У задачи отдельного снимка конфига нет; `TASKS.json` хранит только то, что относится к дереву.
  Исключение — **проектный** слой: `serve` не знает проекта, поэтому `<repo>/.agent/config.toml`
  накладывается на задачу в `start`/`resume` (`config::with_project_file`, D-119). Иначе при
  запуске под launchd (cwd — `/`) проектный файл не читался бы никогда и порядок слоёв выше
  выполнялся бы только у клиента внутри репозитория. `[policy]` из проектного файла не
  применяется и на этом пути.

```toml
# ~/Library/Application Support/immortality/config.toml
[backend]
base_url = "http://llm-server:47832/v1"
model = "swift-iq2_xs"
# Проверено на живом сервере: 502 на prefill может прийти через 300 с,
# успешный prefill 200K занимает 254 с. Меньше 600 ставить нельзя.
request_timeout_secs = 600
connect_timeout_secs = 10
max_inference_concurrency = 1        # принимается и валидируется, но в v0.1 не читается: см. §10
health_interval_secs = 30            # принят, цикла health-check в демоне нет
unavailable_escalate_after_secs = 900 # принят, эскалации по простою в демоне нет
# Модель по умолчанию думает (reasoning_content) и съедает им max_tokens. Проверено:
# отключение убирает reasoning полностью, tool-calling продолжает работать, вызов
# ускоряется в ~2.8 раза.
enable_thinking = false
# Бюджет одного хода. Не путать с loop.max_tokens_per_attempt — тот ограничивает всю
# попытку. 1024 (клиентский дефолт) хватает на вызов инструмента и не хватает на
# write_file с целым файлом в аргументе: ход обрезается, работа выбрасывается (D-125).
max_completion_tokens = 8192

[policy]
workspace_root = "~/rust_projects"
allow_write_globs = [".agent/**", "**"]          # внутри worktree
deny_write_globs = ["**/.git/config", "**/.env*"]
deny_read_globs = []                             # пусто: root и так узкий
deny_programs = []                               # "sudo", "ssh", "curl" — на выбор человека
yolo = false                                     # снимает эскалации, не запреты (D-101)
trusted_hosts = ["llm-server", "127.0.0.1", "localhost"]
allow_commit = true
allow_push = false
allow_network = false
allow_sudo = false
allow_install_deps = true                         # только внутри worktree

[storage]
artifact_ttl_days = 30
log_retention_months = 12
disk_warn_bytes = 1073741824                      # 1 GiB
disk_pause_bytes = 268435456                      # 256 MiB; должен быть меньше warn

[logging]
level = "info"
dir = "~/Library/Logs/immortality"
```

Пять флагов разрешений — отдельные ключи, а не битовая маска: «пусть коммитит», «пусть ходит
в сеть» и «пусть ставит пакеты» — разные решения, и человек должен уметь ответить на каждое
по отдельности. **Статус в v0.1: читается только `allow_network`** — он превращается в
пометку `auto_approvable` у эскалации, а у пометки, кроме тестов, читателей нет. `allow_push`,
`allow_commit`, `allow_sudo` и `allow_install_deps` принимаются и валидируются, но потребителей
не имеют: push и так недоступен инструменту `git`, а `sudo` отсекается `deny_programs`, когда
оператор его туда вписал. Ключи оставлены как контракт на v0.2, а не как работающее поведение.

## 4. Дерево задач и единица контекста

Задача (`task`) — пользовательская цель. Она декомпозируется в дерево подзадач
(`subtask`). Глубина ограничена `loop.max_subtask_depth` (дефолт 2, `validate` не пропускает
больше 3: качество контекста падает). Единица исполнения — **подзадача с чистым контекстом**:

1. Runner собирает контекст только из: цели подзадачи, DoD, релевантных фактов рабочей
   памяти, последнего чекпоинта и истории **этой** подзадачи.
2. Исполнитель работает до выполнения DoD или исчерпания попыток.
3. По завершении пишет структурированный отчёт (`outcome`, `facts`, `files_touched`,
   `rejected_ideas`) в состояние и в журнал. Контекст этой подзадачи после этого не нужен.
4. Следующая подзадача стартует с новым контекстом и видит только состояние.

Это ключ к работе на слабых моделях: сложность хранится в дереве задач и файлах, а не в
окне. Модель никогда не видит 200k токенов истории, даже если сервер это позволяет.

Исполнитель **вправе сам дробить** невыполнимую подзадачу (до глубины 2), если это не меняет
DoD родителя — с записью в журнал и без остановки. Изменение состава верхнего уровня плана
или глобального DoD — это replan, требующий подтверждения человека.

Дробление устроено как «предлагает модель, решает планировщик» (D-078). Модель вызывает
`split_subtask` с заголовком и целью каждого куска; DoD не параметр — дети наследуют
родительский, иначе дробление стало бы способом ослабить гейт ровно там, где подзадача уже
трижды провалилась. Ребёнок, выбросивший обязательную команду родителя (сверка по `id` и по
`command`), потерявший ревьюера, оказавшийся не на той глубине, зависящий от родителя или
оставшийся единственным куском, отвергается до записи файла: `TASKS.json` не меняется и
журнал не получает строки о дроблении, которого не было. Единственный кусок отвергается
отдельно — это та же работа под новым id с новым бюджетом попыток.

Заявка модели (`finish_subtask`) — не успех, а предложение: исход решают три гейта (D-079).
Порядок — дешёвое первым: дифф-санити, команды DoD, reviewer. Любая находка санити и красная
обязательная команда обрывают остальное; reviewer не получает инструментов и одобряет только
явным `approve`. Правила — чистые функции в `core::gate`, I/O — за `Gates` и `Reviewer`, так
что «модель не может объявить успех в обход» — это проверяемое свойство, а не намерение.
Раннер закрывает попытку (`Succeeded` только при зелёном вердикте) и отдаёт вердикт наверх;
`done` в дерево пишет планировщик, потому что дерево — его.

## 5. Жизненный цикл задачи

Счастливый путь: `queued → planning → awaiting_plan_approval → running → verifying →
ready_for_review → merged`. Ветвления — в таблице ниже.

Рёбра — ровно те, что в `TaskState::trigger` (`crates/core/src/domain/task.rs`), и это
единственное место, где они записаны: `every_non_terminal_state_has_an_exit` ловит состояние
без выхода, а `terminal_states_accept_nothing` — попытку выйти из `merged`/`cancelled`.

| Из | Триггер | В |
| --- | --- | --- |
| `queued` | `start_planning` | `planning` |
| `planning` | `plan_written` | `awaiting_plan_approval` |
| `planning`, `awaiting_plan_approval` | `plan_approved` | `running` |
| `running` | `execution_finished` | `verifying` |
| `verifying` | `gates_passed` | `ready_for_review` |
| `verifying` | `gates_failed` | `failed_gates` |
| `failed_gates` | `retry` | `running` |
| `planning`, `running`, `verifying`, `failed_gates` | `block` | `blocked` |
| `blocked` | `unblock` | `running` |
| `ready_for_review` | `merge` | `merged` |
| любое, кроме `merged` и `cancelled` | `cancel` | `cancelled` |

Три пути назад в `running` — одобрение плана, `retry` после проваленных гейтов и `unblock`
после блока; причина видна по триггеру, а не по состоянию. План подтверждается неявно: по
умолчанию планирование не останавливается на человеке, поэтому `plan_approved` легален прямо
из `planning`, а `awaiting_plan_approval` существует для случая, когда человек попросил
посмотреть план до исполнения. `blocked` достижим из `verifying` и `failed_gates`, а не только
из `running`: задача, исчерпавшая попытки, не может пройти гейты, и сочинять ей фиктивный
вердикт гейта значило бы записать в журнал событие, которого не было. `cancel` работает из
любого незавершённого состояния, включая `blocked`, — это человеческое решение, а не ответ
планировщика. `Hold` (`waiting_backend`, `paused_disk`) — не состояние задачи, а пометка
поверх: `running` остаётся `running`, даже когда бэкенд недоступен (D-025).

- `planning` — planner строит `PLAN.md`, `ACCEPTANCE.md`, `TASKS.json`. План по умолчанию
  не требует подтверждения, но человек может открыть его и переписать в любой момент
  (`immortality plan`), в том числе до старта исполнения. **Подхват правки на ходу — задел, а
  не поведение:** `Plan::refresh` умеет сравнить `(mtime, len)` и перечитать файл, но
  продюсера у него нет — `cycle::run` получает план, загруженный один раз в `daemon::start`,
  и правка посреди прогона применяется со следующего `start`, а не с следующей подзадачи.
  Модель предлагает короткие **имена** подзадач и зависимости по именам, а не ULID: компилятор
  (`core::planner::compile`) назначает id, разрешает зависимости и прогоняет тот же
  `plan::validate`, что и загрузчик, — план, который принял планировщик, и план, который
  отвергнет планировщик задач, существовать не могут. `plan --goal` — метод демона (D-090):
  лимит глубины и слот инференса принадлежат ему, а клиент только называет свой cwd.
- `running` — исполнение подзадач по плану.
- `verifying` — гейты DoD по каждой подзадаче: дифф-санити, команды сборки/тестов/линта,
  reviewer-субагент по diff без инструментов. Только зелёный вердикт закрывает подзадачу.
  Дифф подзадачи считается от базового чекпоинта попытки (см. `docs/state-and-recovery.md` §4),
  дифф задачи — от точки ветвления `agent/<task>` (`gates::task_base`, D-123): работа закрытых
  подзадач к этому моменту уже в `HEAD`, и дифф против `HEAD` был бы пустым.
  Проверка, отклонённая политикой, не запускается, не считается пройденной и записывается с
  причиной (`why`), а не с одним `exit_code: null` (D-105).
- `ready_for_review` — задача закончена, её работа лежит коммитами в `agent/<task>`; человек
  делает `immortality merge`. `merge` отказывает, если впереди `HEAD` нет ни одного коммита
  (D-121): «нечего сливать» и «слито» — разные ответы.
- `blocked` — подзадача исчерпала перезапуски; задача не останавливается, а берёт
  следующую независимую подзадачу. Если независимых нет — задача в `blocked` с причиной.
  «Независимая» проверяется деревом, а не наличием `Pending`: подзадача, чья зависимость тоже
  не закрыта, работой не является, и L5 тогда эскалирует, а не ждёт. `Blocked` считается
  закрытым, поэтому одна застрявшая подзадача не простаивает задачу (D-078).

Задача не имеет лимита по общему времени. Лимиты — на попытку и на подзадачу (см. §6),
чтобы одна залипшая подзадача не съедала сутки.

## 6. Агентный цикл и бюджеты

Один шаг = один вызов модели (+ исполнение запрошенных инструментов).

Бюджеты на **попытку** (attempt): `max_steps_per_attempt = 60`,
`max_tokens_per_attempt = 120000`, время — `60 с × max_steps_per_attempt` (то есть ~45 минут
при дефолте). Отдельного ключа для времени нет намеренно: два независимых числа разошлись бы,
как только человек поправит одно.
Бюджеты на **подзадачу**: `max_attempts_per_subtask = 3` попытки и
`max_restarts_per_subtask = 2` перезапуска с откатом. Это два независимых счёта (D-080):
попытка тратит первый, `Restart` — оба, `Retry` — только первый. Останов проверяется
**после** списания, поэтому бюджет в 2 попытки даёт ровно 2 попытки, а не 3.

Остаток бюджета и номер следующей попытки **читаются из журнала** (`restart::Spent`), а не из
дерева: поле `attempts` в `TASKS.json` не пишется продакшном и остаётся мёртвым — бюджет ведёт
журнал. Раньше из-за этого каждый старт процесса начинал с попытки 1 и с полным бюджетом.
Живой `kill -9` показал счёт — два `attempt_started` с одним ключом `(подзадача, 1)`.
`Abandoned` в счёт не идёт (D-027), но номер сдвигает, иначе ключ повторится (D-099).

Отчёт о закрытой подзадаче (`report`), наоборот, **пишется** в `TASKS.json` — при `done` и при
`blocked` ([`core::plan::Plan::set_report`]) — и читается при возобновлении, потому что
`rejected_ideas` должны переживать процесс (D-136).

Журнал один на репозиторий, поэтому бюджет читается по паре **`(задача, подзадача)`**. До D-106
фильтра по задаче не было, и второй прогон `black_jack` (тот же план, те же id подзадач) начал
все шесть подзадач с номера 2 или 4, унаследовав попытки первого прогона; при
`max_attempts_per_subtask = 3` дошло до «попытки 4», а сравнение прогонов стало бессмысленным.

Лестница реакции на проблему:

| Уровень | Действие |
| --- | --- |
| L1 | Инъекция системного сообщения: «ты повторяешься; вот что уже пробовал; смени подход» |
| L2 | Принудительный шаг: «перечисли 3 альтернативные гипотезы, выбери одну, обоснуй» |
| L3 | Перезапуск попытки: откат worktree к последнему зелёному чекпоинту, свежий контекст, другая стратегия в брифе (D-080) |
| L4 | Дробление подзадачи (если глубина < 2): модель предлагает куски, `core::scheduler` проверяет (D-078) |
| L5 | `blocked` для подзадачи, переход к следующей независимой, эскалация человеку |

L3 — не один сценарий, а два решения (`core::restart::decide`):

- **`Retry`** — отказ гейта DoD. Дерево остаётся: ревьюер прочитал дифф и назвал, что в нём не
  так, а откат выбросил бы почти готовую работу. Бюджет попыток тратится, бюджет перезапусков —
  нет.
- **`Restart`** — детектор, бюджет, стойло, пустой ответ, неизвестный инструмент. Дерево
  откатывается к базовому чекпоинту. Тратятся оба бюджета.

Порядок записи — **снимок, журнал, перемещение**: `checkpoint_created {role:"base"}`,
`{role:"discarded"}` (что будет выброшено) и `{role:"rollback"}` (куда возвращаемся) попадают на
диск до `reset`, `attempt_restarted` — после. Крах в этом окне восстанавливается
`recover::interrupted_restart`. В бриф следующей попытки идут причина (`observation` + `advice`),
**исходная** стратегия и накопленный `rejected_ideas`; сгенерированная стратегия не цитируется,
иначе советы вкладываются сами в себя.

Базовый чекпоинт снимается **до первой попытки** подзадачи, а не внутри отката и не «в начале
сеанса». Снятый внутри отката, он содержал бы работу провалившейся попытки: журнал назвал бы её
`base`, откат повёл бы дерево ровно на неё, и он не выбросил бы ничего — а гейт
следующей попытки увидел бы пустой дифф. Поэтому базу читают из журнала
(`core::restart::base_of`): годится только **первая** запись `checkpoint_created {role:"base"}`
подзадачи, а снимок берётся лишь тогда, когда её нет. Сеанс короче подзадачи — сбой бэкенда
закрывает его, не откатывая дерево, — и «база на входе в сеанс» после такого сбоя оказывалась
снимком уже сделанной работы (D-124). Отсутствие базы (репозиторий без коммитов, git отказал) —
остановка с причиной, а не повод снять базу поздно (D-098).

Каждое срабатывание — событие журнала с указанием детектора и уровня. Это же — метрика
качества модели и повод подкрутить пороги.

### 6a. Время — параметр, а не константа (D-081)

Три вещи измеряются стенным временем: бюджет попытки (45 минут при дефолте), TTL артефактов
30 дней и порог эскалации при отказе бэкенда 15 минут (последний сейчас не подключён к демону,
§7 state-and-recovery.md). Ждать их в тесте нельзя, а golden-журнал, у которого `ts`
приходит с машинных часов, — не golden. Поэтому время идёт через трейт `core::time::Clock`:
`SystemClock` в продакшене, `FixedClock` в тестах и симуляторе (заморожен на
`2026-11-12T10:00:00Z`, двигается только явным `advance`). Трейт не глобальный — иначе два
теста в одном процессе делили бы часы, и результат зависел бы от порядка запуска.

```rust
pub trait Clock: Debug + Send + Sync { fn now(&self) -> Timestamp; }
```

Часы принадлежат **журналу** (`Journal::set_clock`/`now()`), а не прокидываются параметром в
каждую функцию. Runner ставит свои часы в журнал на входе в попытку: записи раннера и записи
`ToolCallLog` внутри него обязаны быть упорядочены одним источником. Места, где событие
наблюдается раньше, чем пишется (`record_gate`, `record_checkpoint`), принимают `at`
параметром — `now()` в точке записи сказал бы неправду.

Бюджет меряется как `clock.now() - started`, где `started` — `Timestamp`, а не `Instant`:
бюджет — это стенное время, и фейковые часы должны уметь его двигать. Тест «один шаг
тратит 46 минут за ноль реальных секунд» проверяет именно это.

`Tool::expected_effect(&Args)` — фраза для журнала и `immortality log` про **этот** вызов:
по умолчанию из объявленных путей («write src/parser.rs»), с переопределением там, где эффект
живёт в аргументе («run `cargo test`»). Это не `description()`: описание говорит, что
инструмент *такое*, и не называет ни файла, ни команды.

## 7. Детекторы зацикливания

Все шесть работают одновременно; срабатывание фиксируется в журнале. D1–D4 и D6 живут в
`Signals`/`Stream` и считают шаги и вывод; D5 (бюджет) отдельный — его синтезирует
`AttemptSession::exhausted` из шагов, токенов и времени, и записывается он через
`ending_reaction`, а не через `Signals::react`.

| # | Детектор | Сигнал | Порог (дефолт) |
| --- | --- | --- | --- |
| D1 | Точный повтор | Нормализованный `(tool_name, args)` идентичен предыдущему вызову | 3 → L1, 5 → L2, 8 → L3 |
| D2 | Семантический повтор | Разные вызовы дают одинаковый хэш нормализованного вывода | 2 → L1, 3 → L2 |
| D3 | Отсутствие прогресса | Наблюдение, которого в этой попытке ещё не было, сбрасывает счётчик; повтор любого виденного — шаг без прогресса | 15 → L2, 25 → L3 |
| D4 | Цикл рассуждения | Повтор n-граммы (40 **слов**) ≥ 3 раз в последних 1200 словах. Токенов у процесса нет — бэкенд токенизирует, поэтому окно и n-грамма считаются в словах. Второй сигнал (3 абзаца с SimHash-близостью > 0.9) описан, но не реализован (D-077) | немедленно: оборвать стрим → L2 |
| D5 | Бюджет | Шаги/токены/время попытки | → L3 |
| D6 | Повторная правка файла | `write_file`/`edit_file` в один и тот же путь, без прогресса между ними | 6 → L1, 10 → L2, 16 → L3 |

D4 работает **на стриме**: генерация обрывается до того, как модель дописала 5000 токенов
одного и того же абзаца. Для локальных моделей это критично: они умеют «залипать» в
середине сообщения, и ждать конца ответа бессмысленно.

Нормализация для D1: trim, сортировка ключей JSON, абсолютные пути внутри worktree →
относительные. Пробелы внутри строковых значений **не** схлопываются (`write_file` пишет
тело файла — два разных файла не должны выглядеть одним вызовом), и «волатильные» поля
вроде `ts`/`uuid` не отбрасываются: это то, что инструмент исполнит.

D1 и D2 не дублируют друг друга: одинаковый вызов — это D1, а D2 считает только случаи,
где модель сменила вызов и получила тот же ответ. Иначе один застрявший шаг давал бы две
записи и метрика считала бы один провал дважды.

D3 считает шаги без нового наблюдения: любой вывод, которого в этой попытке ещё не было,
сбрасывает счётчик. Отказ инструмента и проза без вызовов — тоже шаг, но без прогресса.
«Новое» — это **вся попытка**, а не соседний шаг: чередование A-B-A-B, где оба вывода уже
известны, прогресса не даёт, хотя каждый шаг отличается от предыдущего. Именно так застряла
`verify_shuffle_spec` на втором живом прогоне: 62 шага чистого чередования двух `ruby -e`
(`[41, 28, …]` и `[1, 2, …]`), 28 и 25 повторов, а D1/D2 молчали, потому что считают только
подряд идущие совпадения. Замер по обоим прогонам: самая длинная такая серия — 49 шагов в
больной попытке и 0–6 во всех здоровых, поэтому порог 15/25 остался прежним (D-108).

D6 считает **место записи**, а не содержимое: модель, которая девятнадцать раз переписала один
файл разными телами и девятнадцать раз перезапустила одну проверку, невидима для D1 (аргументы
разные), а D2/D3 сбрасываются на каждом новом выводе (проверка печатает случайные данные).
Измерено на первом живом прогоне (`black_jack`): до D6 дело кончилось лимитом шагов. Порог
откалиброван по двум прогонам: здоровый переписывает главный файл не больше трёх раз, больной —
девятнадцать. Серию сбрасывает либо прогресс, либо запись в **другой** путь: измеренная
последовательность чередовала правку с проверкой, и счётчик, смотрящий только на соседние
вызовы, обнулялся бы каждой проверкой (D-104). Оговорка: `Signals::record_progress` —
единственный сброс по «новому факту/зелёному гейту» — в демоне не вызывается, его зовут только
тесты, так что сегодня серию сбрасывает именно смена пути.

Реализация — `core::detect`: `Signals` (D1/D2/D3/D6), `Stream` (D4), пороги из `[detectors]`
в `Thresholds`, решение — `Signals::react`. Детекторы не знают ни журнала, ни модели, поэтому
пороги тестируются таблицей «счётчик → уровень», без бегуна. Второй сигнал D4 (`SimHash` по
абзацам) **не реализован**: у него нет откалиброванного порога, а детектор, срабатывающий на
обычной прозе, приучает игнорировать `detector_fired`. Правило n-грамм ловит измеренный отказ
точно и дёшево, поэтому второго сигнала в v0.1 нет (D-077).

L1 и L2 попытку **не** кончают: они дописывают инструкцию в конец истории (префикс остаётся
неизменным, кэш жив) и продолжают. Попытку кончает L3 или бюджет; срабатывание пишется как
`detector_fired` с детектором, уровнем и метрикой. «Один раз на шаг» — правило `Signals::react`
(он отдаёт только первое совпадение), а не гарантия журнала: шаг, где D4 оборвал стрим, пишет
свою запись до возврата, и `react` может добавить на этот же шаг D3 — две записи с разными
`detector` описывают одно и то же место, и склеивать их нельзя, потому что причины разные.

## 8. Контекст и компактация

Слои промпта (сверху вниз, при переполнении сжимается снизу):

1. **Системный промпт** — строка, собранная в `daemon::start::system_prompt` из цели задачи;
   версионированного файла промпта нет, но в рамках задачи префикс неизменен.
2. **Бриф задачи/подзадачи** — цель, DoD, ограничения, текущая стратегия.
3. **Рабочая память** `.agent/NOTES.md` — факты о кодовой базе, найденные ограничения и
   **отвергнутые гипотезы** (чтобы модель не ходила по кругу). Всегда в промпте.
4. **Дайджест состояния** — выдержка плана, статус дерева задач, последний чекпоинт.
5. **История шагов** — последние N вызовов с усечёнными результатами.
6. **По запросу** — инструменты `read_state`, `grep_journal`, `read_file`.

**Порядок слоёв — не стилистика, а производительность.** Замер на живом бэкенде
(`swift-iq2_xs`, 2026-11, `curl` к `/v1/chat/completions`, `chat_template_kwargs.enable_thinking=false`):

| Префикс | Холодный prefill | Тёплый (тот же префикс) | `cache_n` | Ускорение |
| --- | --- | --- | --- | --- |
| 264 токена | 7.2 с | 0.19 с | 257/264 (97%) | 38× |
| 4 824 токена | 19.2 с | 0.23 с | 4 817/4 824 | 84× |
| 24 024 токена | 75.7 с | 0.19 с | 24 017/24 024 | **400×** |

Холодный prefill масштабируется линейно (~254–319 ток/с), тёплый почти не зависит от
размера: попадание в кэш стоит ~0.05 с на префилл остатка. Любая правка в начале промпта
обнуляет кэш и возвращает линейную цену. Отсюда три правила:

- стабильные слои (1–4) идут первыми и не меняются между шагами;
- `NOTES.md` обновляется батчем на границе подзадачи, а не каждые несколько шагов;
- компактация и смена контекста — осознанная операция с ценой ~1–3 минуты prefill.

Правила:

- Мягкий бюджет 32k → `Verdict::Compact`; жёсткий 64k → `Verdict::Restart` (бюджет
  настраивается, окно сервера 256K — это страховка, не рабочий режим). Раннер реагирует
  только на `Restart` (кончает попытку исходом `Ending::Tokens`); `Compact` он **не**
  исполняет: компактация требует отдельного вызова модели и места, куда писать сводку, а
  раннер, молча выбросивший историю, сломал бы append-only префикс, на котором держится кэш.
  То есть в v0.1 мягкий порог — сигнал, а не действие.
- Учёт токенов: `usage.prompt_tokens` из ответа, если сервер его отдаёт; иначе эвристика
  `chars / 3.5` с поправочным коэффициентом из истории.
- Бюджет попытки считает **прирост**, а не перечитывание: шаг списывает `completion` плюс ту
  часть `prompt`, что больше прошлого шага. Промпт уходит целиком каждый раз, но стабильный
  префикс — уже оплаченные байты; списывать его снова значит превратить
  `max_tokens_per_attempt` в лимит шагов, размер которого зависит от контекста (D-098).
- Результат инструмента больше `max_tool_output_bytes` (8 KiB) сохраняется в
  content-addressed хранилище; в контекст идут голова + хвост + маркер с числом байт, а
  `sha256` артефакта попадает в observation для человека, не как инструкция модели.
- Компактация как отдельная операция (вызов с жёстким шаблоном: факты / решения / открытые
  вопросы / **отвергнутые гипотезы** / где остановились) реализована в `core::context::compact`:
  инструкция с обязательными секциями, парсер, отказывающий при пропущенной или пустой секции,
  и `kind: compaction` в перечислении. Продюсера в демоне нет, поэтому сегодня `Compact` —
  сигнал, который раннер не исполняет. Секция `Rejected` в `NOTES.md` при этом обязательна —
  пустая отвергается, явное `- none` отличимо от «не заполнили» (D-074).

Реализация: `core::context` держит префикс неизменяемым по типам — сеттера у стабильных слоёв
нет, история только дописывается. Мост в wire-сообщения — `immortality-llm::prompt`, потому что
`core` не должен знать `Message`. Усечение: бюджет в байтах, голова + хвост, маркер с числом
байт внутри текста модели; полное тело — в артефакте, и подсказка советует сузить запрос, а не
читать путь, который политика всё равно запретит.

## 9. Протокол инструментов

1. Отправляем нативные `tools` (JSON Schema) + `chat_template_kwargs.enable_thinking`. Ревьюер
   всегда шлёт `false` (`crates/llm/src/wire.rs`); planner и исполнитель шлют значение
   `backend.enable_thinking` из конфига. Планировщику рассуждение окупается — разложить цель на
   шаги та работа, где оно помогает; на шаге исполнения оно тратит тот же бюджет завершения,
   из которого пишется аргумент `write_file` (D-125), поэтому по умолчанию оно выключено и для
   исполнителя тоже.
2. Стрим парсим нативно; аргументы валидируем по схеме **до** исполнения.
   Особенности проверенного бэкенда: аргументы приходят **посимвольными фрагментами**
   по `index`, в потоке встречаются SSE-комментарии `: keep-alive`, а рассуждение идёт
   отдельным полем `reasoning_content` — его нельзя склеивать с `content`.
3. Если модель написала вызов текстом, вызвала несуществующий инструмент, дала битый JSON
   или пустые аргументы — включается fallback-парсер: ```json-блоки, XML-подобные теги,
   «почти-JSON» с починкой (висячие запятые, одинарные кавычки, обрезанный хвост).
4. Невалидный вызов никогда не роняет цикл: модели возвращается структурированная ошибка
   с ожидаемой схемой — это обычное observation.
5. Невалидный вызов пишется в журнал как `invalid_toolcall` — это метрика деградации
   модели и сигнал, что пора сменить профиль. Счётчики `native_toolcall` и `text_fallback`
   объявлены в перечислении `kind`, но продюсеров у них в v0.1 нет.
6. `finish_reason == "length"` при `content == null` и непустом `reasoning_content` —
   отдельный класс отказа (`ModelFault::ThinkingTruncated`): модель «передумала» и не успела
   ответить. Классифицирован как `model_failure`, то есть **не** retryable (D-047): лечение —
   другой запрос (больше `max_tokens`, без reasoning), а не повтор того же. Автоматического
   повтора с `max_tokens ×2` в v0.1 нет — попытка кончается, решение принимает вызывающий.

## 9b. Делегирование: `delegate` и субагент

`delegate` — инструмент, который передаёт один самодостаточный бриф субагенту с чистым
контекстом в том же worktree. Субагент не видит разговор родителя, поэтому всё нужное — в
`brief`; назад приходит структурированный отчёт, и он единственный канал, по которому находки
попадают к родителю.

- **Цикл разорван слотом.** `Runner` держит `Arc<Registry>`, `delegate` живёт в реестре, значит
  инструмент строится раньше раннера. `SubAgentSlot` (`RwLock<Arc<dyn SubAgent>>`) заполняется
  сразу после постройки раннера (`start::wire_delegation`), а не передаётся в конструктор.
  Стартовое значение — `NoSubAgent`, который отказывает: сборка без установки получает ошибку, а
  не пустой успешный отчёт. `RwLock`, а не `OnceLock`, чтобы повторная установка заменяла.
- **Свой журнал, свой каталог.** `Journal` single-writer, а родитель держит писатель на весь
  вызов, поэтому субагент пишет в `delegations/<del_id>/JOURNAL.*.jsonl` — рядом с отчётом и под
  тем же id. Единица восстановления — вызов `delegate`, а не шаги субагента, и проба ищет отчёт.
- **Бюджет шагов — единственное, чем владеет субагент.** `max_steps` приходит из вызова
  (по умолчанию 20, потолок 40); токены и wall-clock он заимствует у родителя, потому что это
  тот же аккаунт. Исчерпание шагов — `Finish::Exhausted`, а не `Done`: родитель по этой разнице
  решает, повторять ли с большим брифом.
- **Гейтов у брифа нет.** `BriefGates` — пустой мир: пустой `Diff` и пустой `DoD` дают `Passed`,
  не обращаясь к миру. Работу судит `DoD` родителя на том же worktree; собственный `RealGates`
  гонял бы acceptance родителя по недоделанному дереву.
- **Вложенность запрещена глубиной.** `Runner::delegation_depth` штампуется в `ToolCtx` каждого
  вызова, `refuse_nested` отвергает при `depth != 0`. Второй реестр был бы вторым местом для
  того же правила.

## 9a. Классификация ошибок бэкенда

Классификация реализована целиком (`llm::failure`); колонка «Действие» говорит, кто его
выполняет. Backoff и эскалация — политика, которая в демоне пока не подключена (§7
state-and-recovery.md).

| Ответ | Класс | Действие |
| --- | --- | --- |
| 429, 5xx | `retryable` | расписание `backoff` 1→60 с, до 6 попыток — реализовано, в демоне не вызывается |
| 502 после длинного prefill (проверено: 300 с на 130K) | `retryable` | длинный backoff; цикл пишет `backend_unavailable` |
| таймаут соединения / обрыв стрима | `retryable` | повтор с тем же телом — то же расписание |
| 400 на схему запроса | `fatal` | исправить запрос; эскалация при повторе — цель |
| `finish_reason: length` + `content: null` | `model_failure` (`ThinkingTruncated`) | новый запрос с большим `max_tokens`, без reasoning; автоматически не повторяется |
| пустой `content` и пустые `tool_calls` | `model_failure` (`EmptyTurn`) | то же; смена профиля — решение человека |

Бюджет одного хода (`backend.max_completion_tokens`, по умолчанию 8192) — не то же, что бюджет
попытки (`loop.max_tokens_per_attempt`): первый ограничивает один ответ модели, второй — всю
попытку. Пока поле не существовало, исполнитель не отправлял `max_tokens` вовсе и действовал
клиентский дефолт 1024, которого хватает на вызов инструмента и не хватает на `write_file` с
целым файлом в аргументе (D-125). Отказ с `ending: "backend"` пишет в `attempt_failed` поле
`detail` — иначе обрезанный ход и мёртвая сеть неразличимы в журнале.

## 10. Конкурентность

- Один `start` на задачу в процессе: слот прогона (`RunSlot`) держится до конца цикла, и второй
  `start` той же задачи получает отказ с именем держателя. Это защита журнала (один писатель),
  а не лимит на число задач.
- **Глобального семафора инференса в v0.1 нет.** `backend.max_inference_concurrency` есть в
  конфиге и валидируется, но ни один код его не читает: два `start` двух разных задач дадут
  два параллельных потока и два запроса к модели. Сегодня это ограничивает человек, а не
  демон; запись в конфиге — заявка, которую надо либо подключить, либо убрать.
- Внутри задачи шаги последовательны (петля агента): следующий запрос начинается после того,
  как результат предыдущего записан в журнал.
- Все рабочие каталоги изолированы worktree на задачу, поэтому параллельные задачи не делят
  дерево. `seq` журнала считается по файлу проекта, и две задачи одного проекта пишут в один
  `JOURNAL.jsonl`. **Одного писателя на файл никто не обеспечивает:** `Journal::open` открывает
  файл в append-режиме без `flock`, а `RunSlot` держится на задачу, а не на проект, поэтому два
  параллельных `start` двух задач одного проекта дадут два писателя и два `seq` с одним
  номером. Сегодня это держится тем, что человек запускает по одной задаче; блокировка — задел
  на v0.2.
- Очередь отвечает на **два разных вопроса** (D-087): «кто берёт слот инференса» и «кто
  делает офлайн-работу». Полный порядок — приоритет → возраст → id, не зависящий от порядка
  входа; задача, обслуженная последней, уходит в конец своей приоритетной группы, чтобы равные
  чередовались. **В проде это пока вырожденный случай:** все кандидаты строятся с
  `Priority::Normal` (`daemon::scheduling`), `note_served` в проде не зовётся, а `status`
  каждый раз создаёт свежую `Queue::new()`, поэтому `last_served` всегда `None` и ротация не
  срабатывает. Порядок фактически — возраст → id.
  Диспетчера, который бы эту очередь исполнял, в v0.1 нет: `next_for_inference` зовёт только
  `status`, чтобы объяснить простой, а `next_for_offline` не зовёт никто (см. §7 в
  state-and-recovery.md).
- `status` несёт причину простоя (`scheduling.reason`), собранную теми же правилами:
  «N waiting for the model backend», «N with no subtask left to run», «paused on free disk
  space». Молчащий простаивающий демон и пустая таблица — тот отказ, ради которого проект
  существует.
- Один демон на пользователя: `daemon.lock` в корне каталога состояния, второй `serve`
  отказывает и называет pid держателя. Замка на **проект** нет — второй демон на том же
  проекте не стартует лишь потому, что не стартует второй демон вообще.

### 10a. Фоновый запуск: `LaunchAgent` / `systemd --user`

Один и тот же контракт CLI, два бэкенда (D-012, D-086, D-110). На macOS демон ставится как
`LaunchAgent` (`dev.immortality.daemon`) с `KeepAlive`, `RunAtLoad` и `ThrottleInterval = 10`;
агент живёт в `~/Library/LaunchAgents/`, plist генерируется из абсолютных путей бинаря, каталога
состояния и лога. На Linux — `systemd --user`-юнит с `Restart=on-failure` и `RestartSec=10` в
`$XDG_CONFIG_HOME/systemd/user/`, включённый симлинком в `default.target.wants`.

Обе определены в `daemon::service`, общее (`LABEL`, задержка рестарта, `ServiceSpec`, `Status`,
`Installed`) вынесено в `mod.rs`, различие — в `launchd.rs` и `systemd.rs`. Оба модуля
компилируются всегда; `pub use` выбирает один.

- `immortality service install` — пишет определение и запускает демон. Идемпотентна:
  неизменённое определение не трогается, работающая задача не перезапускается (это убило бы
  идущую попытку), изменённое — перезапускается (`bootout` → `bootstrap` на macOS,
  `daemon-reload` → `restart` на systemd).
- `immortality service uninstall` — останавливает и удаляет вместе со ссылкой включения.
  Идемпотентна.
- `immortality service status` — сообщает `installed` и `running` **раздельно**: упавшая задача
  внутри окна throttle установлена и не работает. Путь к определению — поле `unit` (на macOS
  алиас `plist` сохранён для скриптов `0.1.2`).

`serve` в foreground остаётся: это режим отладки и то, что запускает сам агент.

## 11. Наблюдаемость

- `tracing`: JSON-строки в месячные файлы плюс человекочитаемый слой в stderr; уровень
  задаётся `--log-level` или `[logging] level`. Фоновый демон под `launchd` пишет stderr в
  свой лог, поэтому одна и та же настройка работает в обоих режимах.
- Журнал событий (см. state-and-recovery.md) — источник и для `immortality log`, и для
  метрик, и для регрессионных тестов.
- Команды, которым нужно состояние демона (`plan`, `log`, `metrics`, `gc`, `merge` и остальные),
  — методы демона (D-088): только у него есть лимит глубины плана, живой набор незавершённых
  задач и право писать в журнал. `gc` и `merge` при этом пишут: первый удаляет артефакты и
  крутит логи, второй вливает ветку задачи.
  Клиент присылает свой cwd, потому что cwd демона под launchd — `/`. `metrics` считает из
  журнала, а не из файла, который человек поддерживает: число в `docs/metrics-v0.1.md` должно
  быть воспроизводимо тем, у кого есть журнал (D-092).
- Вещание событий — `broadcast` с ограниченным буфером; отставший клиент **догоняет из журнала**
  от своего последнего `seq`, а не теряет соединение (D-089). Журнал — единственный источник
  правды, поэтому догон и живой поток отдают одно и то же, а watermark отсекает дубли.
- `doctor` проверяет: загрузку и предупреждения конфига, доверенный хост бэкенда
  (`policy.trusted_hosts`), `GET /v1/models` и наличие настроенной модели, TTFT и **cache hit
  rate** (главная метрика здоровья: без попаданий в кэш каждый шаг стоит минуты), свободное
  место под каталогом логов, запись в этот каталог, существование сокета и его права.
  Диагностик ровно столько, сколько в `doctor::run`; «версия конфига» и «доступность
  launchd-агента» в этом списке отсутствуют — последнее проверяет `service status`.
- Метрики на задачу (`core::metrics`): закрытия с зелёными гейтами, длиннейшая серия
  подряд, срабатывания детекторов по парам `детектор/уровень`, эскалации, перезапуски,
  число записей журнала и целостность цепочки. Отдельно — три числа про потерянную работу:
  зелёные попытки, чья подзадача не закрылась; попытки, кончившиеся по шагам, о которых гейты
  не спрашивали; и попытки, закрытые гейтами после исчерпания бюджета шагов. Шагов, токенов и
  времени в метриках **нет** — они зависят от железа и не публикуются (D-092). Три числа про
  потерю читаются вместе: «ноль потерянного» на журнале, где гейтов не спрашивали, означает
  «неизвестно», а не «ничего не потеряно».

## 12. Безопасность на macOS

Namespaces/контейнеров нет, поэтому защита строится из четырёх слоёв:

1. **worktree на задачу** + ветка `agent/<task-id>` — изоляция изменений и мгновенный откат.
2. **Path allowlist** — запись только в worktree задачи; deny-глобы на `.git/config`,
   `.env*`, глобальный конфиг и `JOURNAL*`, плюс читательский deny-список `deny_read_globs`
   и запрет программ `deny_programs` (D-100).
3. **Классификатор команд** — `read` / `mutate` / `external`; единая точка проверки политики
   для всех инструментов (см. tools-and-policy.md).
4. **Очередь эскалаций** — `external` и необратимое никогда не исполняется автоматически;
   агент видит «ожидает решения» и продолжает работу по остальному плану.

Сокет демона: `0600`, токен в отдельном файле с `0600`. Каталог состояния создаётся с `0700`
(`core::paths::create_private_dir`), и это касается только каталогов, созданных самим процессом:
существующий каталог сохраняет режим, выбранный пользователем, потому что молчаливое ужесточение
прав на чужом каталоге — сюрприз, а не защита. Токен чеканит первый `serve` и больше никогда не
переписывает; второй экземпляр останавливается на `daemon.lock` раньше, чем коснётся сокета
живого демона (D-073).
