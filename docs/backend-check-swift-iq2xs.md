# Проверка бэкенда: Strata + `swift-iq2_xs`

Дата проверки: 2026-11-12. Хост `llm-server` → `192.168.1.70:47832`.
Все цифры получены прямыми запросами к `/v1/chat/completions`, без прокси и без нашего кода.

## 1. Итог

**Сервер рабочий.** OpenAI-совместимый API, нативный tool-calling, стриминг, кэш
префикса, 256K контекста. С проектной точки зрения пригоден, но **не такой, как
предполагалось**: модель думает (reasoning) по умолчанию, скорость низкая, кэш требует
строгой дисциплины промпта.

| Проверка | Результат |
| --- | --- |
| DNS `llm-server` | ✅ `192.168.1.70` |
| ICMP | ❌ заблокирован (нормально, не показатель) |
| `GET /v1/models` | ✅ 200, модель `swift-iq2_xs` (`Swift 1.5 IQ2_XS`, `owned_by: strata`) |
| Chat completions | ✅ 200 |
| SSE-стриминг | ✅ с `: keep-alive` комментариями |
| Нативный tool-calling | ✅ валидный JSON в аргументах |
| Tool-calling в стриме | ✅ посимвольные фрагменты аргументов по `index` |
| Мультиходовой цикл (tool → tool) | ✅ корректно |
| Кэш префикса | ✅ работает, но с оговорками |
| Контекст 256K | ✅ 200K подтверждено |
| `enable_thinking: false` | ✅ работает, убирает reasoning полностью |

**Единственный доступный эндпоинт** — `/v1/models` и `/v1/chat/completions`. `/props`,
`/slots`, `/metrics`, `/health` → 404. То есть **размер окна и число слотов из API не
узнать** — только эмпирически (что я и сделал) или из конфига сервера.

## 2. Решающие находки

### 2.1 Модель думает по умолчанию, и это съедает бюджет

Ответ содержит **два разных поля**: `content` и `reasoning_content`. Reasoning идёт
первым и расходует `max_tokens`.

Практический пример: вопрос «найди баг в функции» при `max_tokens: 400` дал
`finish_reason: length`, `content: null` — **модель потратила все 400 токенов на
рассуждение и не успела ответить**. С `max_tokens: 2000` тот же вопрос дал ответ за
1510 токенов (4584 символа reasoning).

Это ровно тот класс отказа, который мы проектировали детектировать: ответ обрезан,
полезного результата нет, токены сожжены.

**Решение принято:** по умолчанию отправлять `chat_template_kwargs: {"enable_thinking": false}`.
Проверено: reasoning исчезает полностью, tool-calling продолжает работать (10 с вместо
28 с на том же вызове).

```json
{"chat_template_kwargs": {"enable_thinking": false}}
```

Reasoning включаем точечно — только для planner/ревьюера, если качество декомпозиции
окажется недостаточным без него. Это профиль в конфиге, не хардкод.

### 2.2 Скорость: prefill — узкое место, не decode

| Сценарий | Prefill | Decode |
| --- | --- | --- |
| 54 токена | 39 tok/s | 35 tok/s |
| 2.5K токенов | 110–157 tok/s | 34–65 tok/s |
| 7.5K токенов | 354 tok/s | — |
| 50K токенов | 393 tok/s | — |
| 66K токенов | 398 tok/s | — |
| 95K токенов | 356 tok/s | — |
| 129K токенов | ~350 tok/s | — |
| 200K токенов | ~340 tok/s | — |

**Холодный prefill 50K = 127 секунд. 200K = 254 секунды.** Маленькие промпты
нееффективны (39 tok/s на 54 токенах из-за оверхеда), большие стабилизируются около
350 tok/s.

Следствие для дизайна: **бюджет 32K/64K, который мы выбрали, — правильный не только по
качеству, но и по времени.** Пересборка 64K контекста с нуля стоит ~3 минуты. Если бы
мы лили 200K «потому что влезает», каждый шаг агента стоил бы 8+ минут только на prefill.

### 2.3 Кэш префикса: работает, но требует стабильного префикса

Самое важное открытие. Поведение **бинарное**: либо кэш почти полностью попадает, либо
не попадает вовсе. Промежуточных значений нет.

Стабильный префикс (одинаковый system prompt, меняется только вопрос):

```
call1: cache_n 0,     prompt_n 30062  →  95.0 с
call2: cache_n 30043, prompt_n 19     →   0.24 с
call3: cache_n 30043, prompt_n 19     →   0.23 с
```

**Ускорение в 400 раз.** Но если промпт меняется в начале (я менял тело сообщения перед
одинаковым хвостом), кэш промахивается: `cache_n 0, prompt_n 2566 → 23 с`.

Кэш **кэпится**: на 110K-промпте `cache_n = 81920`, на 120K — `98304`, на 200K —
`114688`. То есть кэшируется не больше 80–115K, остальное пересчитывается.

**Следствия, которые надо зафиксировать в архитектуре:**

1. **Порядок слоёв промпта — не стилистика, а производительность.** Стабильное
   (system prompt, бриф задачи, `NOTES.md`) обязано идти первым и не меняться между
   шагами. Переменное (история шагов, результаты инструментов) — строго в конце.
2. **`NOTES.md` нельзя переписывать каждые несколько шагов.** Каждая правка начала
   промпта обнуляет кэш и стоит минуты. Записывать в рабочую память — только на границе
   подзадачи, батчем.
3. **Компактация контекста обнуляет кэш.** Это ещё один аргумент за свежий контекст на
   подзадачу вместо непрерывной истории: нового префикса всё равно не избежать, но
   делаем это редко и осознанно.
4. **`doctor` должен мерить cache hit rate.** Это главная метрика здоровья бэкенда.

### 2.4 Параллелизм: 4 слота

4 одновременных запроса отработали за 2.3 с (по отдельности ~1.7–2.2 с). Два запроса по
300 токенов параллельно: 8.3 с и 11.5 с (последовательно было бы ~5 + ~9 с). Значит,
**сервер обрабатывает несколько запросов одновременно**, но с падением throughput на
каждый.

Это подтверждает решение D-008: **инференс последовательный**. Параллелить запросы к модели
смысла нет, выигрыша не будет, а качество может пострадать. Параллелизм — только на
инструментах, не требующих модели. В v0.1 семафора в коде нет: последовательность держится
тем, что демон ведёт одну задачу за раз (`RunSlot`), а `max_inference_concurrency` не читается.

### 2.5 Транзиентные сбои на очень больших промптах

Промпт ~130K (13 000 повторов строки) один раз вернул **502 `fetch failed` после 303
секунд**, при этом сам сервер остался жив (`/v1/models` → 200 сразу после). Повторный
запрос на 131K прошёл успешно за 42 с.

Это важнее, чем кажется: **на больших prefill сервер может отдать 502 по таймауту**.
Классификация ошибок должна считать такой 502 `retryable` с длинным backoff, а не
`fatal`. И общий таймаут запроса в нашем конфиге (`request_timeout_secs = 600`) взят
правильно — 300 с не хватило бы.

### 2.6 Качество модели

Что проверено:

| Задача | Результат |
| --- | --- |
| Tool-call с одним параметром | ✅ идеально, 10 с с выключенным reasoning |
| Мультиходовой вызов (read → write) | ✅ корректный полный контент файла, валидный JSON |
| Найти реальный баг (`max_of` инициализирован нулём) | ✅ правильный ответ с объяснением |
| Ложноположительный баг-репорт | ✅ корректно ответила `NO BUG` |
| Арифметика 17×23 | ✅ 391 |
| Явная провокация зацикливания | ✅ остановилась сама на 4 повторах |

Модель **не тупая**: на типовых задачах отвечает точно, tool-calling делает аккуратно.
Главные риски — скорость и reasoning, а не качество.

## 3. Что это меняет в дизайне

| Решение | Было | Стало |
| --- | --- | --- |
| Reasoning | не учитывался | по умолчанию `enable_thinking: false`; профиль для planner может включать |
| Бюджет промпта | 32K/64K «по качеству» | 32K/64K **подтверждено замером**: 64K cold = 166 с |
| Порядок слоёв промпта | логический | **обязателен для кэша**: стабильное первым |
| `NOTES.md` | обновляется по ходу | только на границе подзадачи, батчем |
| `request_timeout_secs` | 600 | 600 подтверждено (502 на 300 с) |
| 502 на больших промптах | `fatal`? | `retryable` с длинным backoff |
| `doctor` | общая диагностика | + замер cache hit rate и TTFT — главные метрики |
| Парсер стрима | склейка `tool_calls` | + игнор `: keep-alive` и `reasoning_content` |
| Число слотов | неизвестно | 4 подтверждено; в v0.1 параллелизм ограничен отсутствием диспетчера, а не семафором |

## 4. Что надо уточнить у владельца сервера

1. **Реальный размер окна.** Я подтвердил 200K, но `n_ctx` в конфиге может быть 256K —
   из API это не видно (`/props` → 404).
2. **Квантование и модель.** `IQ2_XS` — это агрессивное квантование. При 2-3 битах на
   вес качество на сложных задачах будет заметно хуже, чем на Q4. Если есть возможность
   поднять до Q4 при том же объёме RAM — стоит сравнить.
3. **Скорость prefill.** 350 tok/s — низковато для 27B-класса. Возможно, влияют флаги
   запуска (`--batch-size`, `--ubatch-size`, flash-attention). Стоит проверить.
4. **Есть ли второй порт/инстанс** для утилитарных задач (компактация), чтобы не
   занимать основной слот.

## 5. Как воспроизвести проверку

Скрипт-заготовка для `doctor` (числа, которые он должен печатать):

```sh
BASE=http://llm-server:47832/v1

# 1. модель и доступность
curl -sS -m 10 $BASE/models | jq -r '.data[].id'

# 2. TTFT и скорость на коротком промпте
curl -sS -m 120 $BASE/chat/completions -H 'Content-Type: application/json' -d '{
  "model":"swift-iq2_xs",
  "messages":[{"role":"user","content":"Say OK"}],
  "max_tokens":32,"temperature":0,
  "chat_template_kwargs":{"enable_thinking":false}
}' | jq '.timings | {prompt_n, prompt_per_second, predicted_per_second, cache_n}'

# 3. cache hit rate: два одинаковых префикса подряд
#    ожидание: второй вызов cache_n ≈ длине префикса

# 4. tool-calling
#    ожидание: finish_reason == "tool_calls" и валидный JSON в arguments

# 5. reasoning
#    ожидание: с enable_thinking:false поле reasoning_content отсутствует
```

модель в tool-calling) закрыта положительно.
