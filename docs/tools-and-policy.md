# Инструменты и политика

## 1. Единая точка проверки

Все инструменты проходят через один `PolicyGate`:

```rust
pub enum Effect {
    Read,        // ничего не меняет вне процесса
    Mutate,      // меняет файлы, git, процессы — в пределах worktree
    External,    // выходит за пределы машины или необратимо
}

pub trait Tool {
    fn name(&self) -> &'static str;
    fn schema(&self) -> &'static serde_json::Value;
    fn description(&self) -> &'static str;                      // для списка инструментов в промпте
    fn idempotency(&self, args: &Args) -> Idempotency;          // Idempotent | ByContent | Unknown
    fn effect(&self, args: &Args) -> Effect;                    // может зависеть от аргументов
    fn paths(&self, args: &Args) -> Vec<PathUse>;               // что трогает вызов, для гейта
    fn expected_effect(&self, args: &Args) -> String;           // про ЭТОТ вызов, для журнала (D-081)
    fn execute(&self, ctx: &ToolCtx, args: Args) -> Result<ToolResult, ToolError>;
    // probe живёт отдельно: recovery спрашивает инструмент по записи журнала, без запуска
}
```

`expected_effect` — не `description`. Описание говорит, что инструмент *такое* («Write a complete
file…»), и одинаково для всех вызовов; ожидаемый эффект называет файл, команду или вопрос —
именно его читает человек в `immortality log` и именно его цитирует recovery, когда не может
понять, подействовал ли прерванный вызов. По умолчанию строится из `paths` («write
src/parser.rs»), инструменты с эффектом в аргументе переопределяют («run `cargo test`»).
Фраза всегда одна строка не длиннее 120 символов.

`PolicyGate` спрашивают двумя способами, и оба возвращают `Verdict` (`Allowed` / `Escalated` /
`Denied`):

- `check(effect, paths)` — вызов без команды: `Read` → `check_reads`, `Mutate` → `check_writes`,
  `External` → эскалация (или `check_writes` при `yolo`, см. ниже).
- `check_command(command)` — `shell`: сначала классификатор, потом `check` по его эффекту.
  Доверенный хост снимает **сетевую** часть, пути остаются под проверкой.

```rust
pub fn check(&self, effect: Effect, paths: &[PathUse]) -> Verdict
pub fn check_command(&self, command: &str) -> Verdict
```

Порядок решений:

1. `Effect::Read` → разрешено, если путь внутри `workspace_root` и не попадает в
   `deny_read_globs` (D-100).
2. `Effect::Mutate` → path allowlist + `deny_write_globs` + правило «только внутри worktree».
3. `Effect::External` → эскалация, никогда не исполняется автоматически. `allow_network` (и
   доверенный хост) вычисляет пометку «эту эскалацию можно было бы одобрить» (`auto_approvable`),
   но `Verdict` от этого не меняется, пути не отменяются, и читателей у пометки вне тестов нет.
   Доверенный хост снимает только **сетевую** часть вопроса и только для `shell`.
4. Любая попытка выйти за `workspace_root` → `Denied` — это observation модели, а не отдельное
   событие журнала (отказ виден как `tool_call_failed` с причиной).
5. `deny_programs` проверяется **до** пунктов 1–4 и до сокращения для `trusted_hosts`: программа
   из списка не запускается ни при каких флагах (D-100).
6. `yolo` (глобальный конфиг или `IMMORTALITY_YOLO=1`) снимает **вопрос** об external-действии:
   ветка `External` уходит в `check_writes`, то есть `curl x > /etc/passwd` по-прежнему отказ.
   Запреты, границы worktree и `Denied` флаг не отменяет (D-101).

Пункт 2 знает одно исключение: перенаправление в устройство-приёмник (`/dev/null`, `/dev/stdout`,
`/dev/stderr`, `/dev/zero`, `/dev/full`) — не путь, и проверять его не нужно. Точное совпадение
имени, не префикс: `/dev/null.txt` и `/dev/sda` остаются путями. Эффект при этом остаётся
`Mutate`, а `echo x > /dev/null; echo y > /etc/passwd` по-прежнему отказ — приёмник пропускается,
остальные пути судятся как обычно (D-102).

Второе исключение — пять документов состояния под `.agent/` (`PLAN.md`, `ACCEPTANCE.md`,
`TASKS.json`, `DECISIONS.md`, `NOTES.md`). Их пишет только `update_state`, и он спрашивает
`check_state_write`, который намеренно идёт мимо `check_writes`: иначе правило запретило бы сам
`update_state`. Обычный `write_file`/`edit_file` на `.agent/NOTES.md` — отказ с указанием на
`update_state` и `read_state`. Причина в D-103: `update_state` пишет **проектную** копию, а
`write_file` разрешается внутри worktree, и один документ получил бы две версии. Запрет не
распространяется на корневой `NOTES.md` и на имена вне `.agent/` — там это обычные файлы (D-107).

`Denied` — это observation модели, а не падение: она получает «действие запрещено
политикой, причина X, разрешённые альтернативы Y».

### Что считается путём в команде

Классификатор извлекает пути не из всей строки, а из аргументов, которые по грамматике программы
являются файлами. У `grep`/`egrep`/`fgrep` первый не-флаговый операнд — **паттерн**, а не путь;
при `-e`/`-f` паттерн приходит из флага, и первый операнд снова файл (D-105). Без этого
`grep -qE '~> *3\.4' README.md` — обычная DoD-проверка — отклонялась политикой, потому что `~` в
аргументе инструмента запрещён намеренно, и проверка не запускалась вовсе.

### Отказ в проверке DoD

Проверка, которую политика отклонила, не запускается и не может считаться пройденной. В журнале
она остаётся записью `gate_result` с `exit_code: null`, `passed: false` и полем `why` — первой
строкой причины («the policy refused this command: …»). Бриф следующей попытки говорит
`` `check_readme` did not run: <причина> ``, а не `(no exit code)`: «провалилась» и «не
выполнялась» — разные факты, и модель, которая их путает, правит уже правильный код (D-105).

## 2. Каталог v0.1

### Чтение (Effect::Read)

| Инструмент | Параметры | Примечания |
| --- | --- | --- |
| `read_file` | `path`, `offset`, `limit` | Нумерация строк; отказ на бинарных файлах с подсказкой |
| `glob` | `pattern`, `path`, `limit`, `include_hidden` | Сортировка по mtime, лимит результатов |
| `grep` | `pattern`, `path`, `glob`, `regex`, `context_before`/`context_after`, `limit` | `pattern` по умолчанию ищется буквально; `regex: true` включает регексы. Поиск идёт только по текстовым файлам |
| `read_process` | `handle`, `max_bytes`, `stream` | Дочитывает вывод с прошлого опроса и сообщает, жив ли процесс. `max_bytes` ≤ 65536 (дефолт 16384), `stream` — `stdout`/`stderr`/`both` |
| `read_state` | `file`, `offset`, `limit` | Пять документов `PLAN.md` / `ACCEPTANCE.md` / `TASKS.json` / `DECISIONS.md` / `NOTES.md` из **проектного** `.agent/` (D-065, D-103) |
| `grep_journal` | `query`, `since_seq`, `kind`, `limit` | Поиск по журналу; `next_seq` — курсор для следующей страницы (D-066) |
| `git` с `subcommand` = `status`/`diff`/`log`/`show`/`rev_parse` | `args` — массив argv | Только чтение |

### Изменение (Effect::Mutate)

| Инструмент | Параметры | Идемпотентность |
| --- | --- | --- |
| `write_file` | `path`, `content` | ByContent; `.agent/<пять документов>` — отказ, их пишет `update_state` (D-107) |
| `edit_file` | `path`, `old`, `new`, `replace_all` | ByContent; те же имена — подсказка про `update_state`, а не «создай `write_file`» (D-107) |
| `git` с `subcommand` = `add`/`commit`/`branch`/`worktree`/`stash` | `args`, `message`, `path`, `reason` | commit → Unknown (probe по `Immortality-Call` trailer); остальные подкоманды — Idempotent |
| `update_state` | `file`, `content`, `replace` | ByContent; `NOTES.md`/`DECISIONS.md` создаются, план-документы — нет; урезать вдвое без `replace` нельзя (D-065, D-103) |
| `shell` | `command`, `cwd`, `timeout_secs`, `env` | Unknown **всегда**: `cargo test` пишет в `target/`, упавший вызов неотличим от несостоявшегося (D-026) |
| `start_process` | `command`, `cwd`, `env`, `name` | Unknown (probe по маркеру в командной строке, D-061) |
| `kill_process` | `handle` | Idempotent |
| `delegate` | `brief`, `scope`, `max_steps` | Unknown (probe по файлу отчёта, D-068); в проде за `NoSubAgent` — см. ниже |

`git` — один инструмент с закрытым перечислением подкоманд (D-063), а не восемь отдельных.
`push`, `fetch`, `pull`, `clone`, `remote` и `config` в перечисление не входят: человек делает
push и merge, а `.git/config` уже в built-in deny-списке. Команды выполняются в worktree
задачи, путь берётся у gate, а не из аргументов. Общие ref'ы ограничены (D-064): `branch`
умеет только листить и создавать, `stash` — только добавлять и применять; `branch -D` из
worktree задачи удаляет ветку в чекауте человека — замерено.

`edit_file` — точная замена строки, по образцу read-tool'ов: если `old` не найден или
найден неоднократно, возвращается структурированная ошибка (модель должна уточнить
контекст), а не «первое вхождение». Это заметно снижает класс ошибок «исправил не то».

### Внешнее (Effect::External)

| Инструмент | Поведение |
| --- | --- |
| `escalate` | Создать запрос человеку: `key`, `question`, `kind`, `options` (D-067) |
| любой сетевой доступ | Только через эскалацию; доверенный хост снимает сетевую часть вопроса у `shell`, но не отменяет проверку путей |

`delegate` в этой таблице отсутствует намеренно: он объявлен `Effect::Mutate`, а не
`External`, потому что пишет один отчёт в каталог состояния демона и ничего не трогает вне
него. Файловые, git- и shell-вызовы субагента проходят через тот же `PolicyGate` по одному.
`scope` — не пожелание: пути отчёта, вышедшие за него, возвращаются родителю списком
`scope_violations` и предупреждением в тексте; сами изменения не откатываются — это решает
родитель. `scope` нормализуется (без `~`, абсолютных путей и `..`) и сравнивается
покомпонентно, поэтому `src` не покрывает `srcfoo`. `max_steps` по умолчанию 20, потолок 40:
бриф, которому нужно больше, — это подзадача, а не делегирование. Вложенное делегирование
запрещено: `ToolCtx::with_depth` помечает контекст субагента, и `delegate` отказывает на
любой глубине больше нуля. Отчёт — `delegations/<del_…>.json` под каталогом задачи, id
выводится из `call_id` (D-068).

**Чего нет в проде.** `ToolsetDeps` создаётся с `NoSubAgent`, а `delegating()` в проде не
зовётся: живой `delegate` отказывает с `no_sub_agent` и советом сделать работу самому или
раздробить её планировщиком. Весь описанный механизм — отчёты, `scope_violations`, вложенный
запрет — реализован и покрыт тестами, но прогон его не исполняет. Это важно для чтения
отчётов: `delegations/` в каталоге задачи появится только когда субагент будет подключён.

### Завершение и дробление

Два «вызова», которые видит модель, не являются инструментами в реестре: у них нет
эффекта, который можно исполнить, и раннер перехватывает их до общего пути (D-076, D-078).

| Вызов | Поведение |
| --- | --- |
| `finish_subtask` | Заявляет выполнение DoD. Попытку **не** закрывает: `Succeeded` означает «гейты прошли», и оценивать свою работу раннер не вправе |
| `split_subtask` | Предлагает куски (заголовок и цель). DoD не параметр — дети наследуют родительский, решение принимает `core::scheduler` |

Отдельного `finish_task` нет: задача закрывается сама, когда закрыты все подзадачи, а
`ready_for_review` выставляет планировщик.

## 3. Terminal

`shell` — **процесс на команду**, а не persistent shell (D-058): каждый вызов запускает
`/bin/sh -c` в собственной группе процессов, поэтому таймаут убивает группу, а не только
прямого ребёнка (иначе осиротевший внук переживает «убийство» и продолжает писать в worktree).

- **`cwd` переживает вызовы, `env` — нет.** Команда оборачивается так, что после её работы
  в маркер пишется `$PWD`, и следующий вызов стартует оттуда; `cd` внутри одной команды
  работает, `export` не сохраняется в принципе, и наблюдение говорит об этом прямо.
  Переменные на один вызов передаются аргументом `env`.
- **stdin закрыт (`/dev/null`).** Команда, которая ждёт ввода, получает EOF и падает за
  секунду с настоящей ошибкой вместо того, чтобы повесить цикл.
- **Таймаут на вызов**: по умолчанию 120 с, модель может попросить до 600 с; большее
  зажимается до потолка. По истечении группа получает SIGTERM, через 5 с — SIGKILL, и
  возвращается структурированный результат `timeout` с тем, что успело выйти: таймаут — это
  результат, а не ошибка, потому что «команда шла 120 с и была убита» и «команда не
  запускалась» требуют от модели разных следующих шагов.
- **Фоновых задач `shell` не оставляет.** Всё, что команда запустила в фоне, доживает до её
  конца в той же группе и убивается; наблюдение об этом сообщает, а для долгоживущего нужен
  `start_process`, который возвращает `handle`. Молча исчезнувшая фоновая задача была бы
  своей ложью.
- **Ограничение вывода**: всё пишется в artifact файлом (не через pipe — заполненная труба
  блокирует писателя). В контекст идут заголовок `--- stdout ---` / `--- stderr ---`, хвост
  канала, строка «… N earlier line(s) not shown» для отрезанного и одна сводка
  `[exited <code> in <secs> s, N line(s) …]`. Извлечения ошибок и разбора `file:line` нет:
  отбор релевантного — работа модели, а не инструмента.
- **Классификатор** (`classify.rs`) решает по программе и подкоманде:
  `read` — `git status`/`diff`/`log`, `ls`, `cat`, `grep`, `rg`, `cargo metadata`/`tree`;
  `mutate` — `mkdir`, `mv`, `sed -i`, `cargo build`/`test`/`check`/`clippy`/`fmt` (они пишут
  `target/` и исполняют код сборки — D-026);
  `external` — `curl`, `wget`, `ssh`, `scp`, `brew`, `sudo`, `git push`/`fetch`, а также
  `npm`/`pnpm`/`yarn`/`bun test|run|install` (чужой менеджер пакетов может сходить в сеть).
  Незнакомая команда консервативно считается `external`.
- **Особого случая `localhost` нет.** Классификатор не смотрит на адреса; хост извлекается
  только если в команде есть схема или порт, и тогда **все** упомянутые хосты обязаны быть в
  `trusted_hosts` (там по умолчанию `localhost` и `llm-server`). `curl localhost` без порта
  хоста не даёт и уходит в эскалацию.

## 4. Эскалации

Очередь, которую агент видит как pending. Форма:

```json
{
  "id": "esc_01JB...",
  "key": "network:example.com:fetch-docs",
  "task": "tsk_01JB...",
  "kind": "external_action" | "blocked" | "backend_unavailable" | "journal_corrupt" | "disk",
  "question": "Разрешить загрузку …?",
  "options": ["allow_once", "allow_for_task", "deny"],
  "blocking": false,
  "created_at": "...",
  "resolved_at": null,
  "answer": null
}
```

Правила:

- `blocking: false` (по умолчанию) — агент продолжает работу по другим подзадачам.
- Дедуп по `key`: одинаковый вопрос не задаётся дважды.
- Ответ человека — запись в `escalations.json` (и, когда подключён `JournalQueue`, — событие в
  журнал). **`allow_for_task` сегодня не влияет на политику:** `EscalationStore::allowance`
  реализован, но `PolicyGate` его не спрашивает, поэтому повторное действие снова уходит в
  эскалацию. Заготовка честно называется заготовкой.
- Эскалация — не конец прогона. Человек может ответить из `immortality escalations`
  в любой момент, даже посреди работы.
- macOS-нотификация (`osascript`) на открытие эскалации: `MacNotifier` реализован, но
  `ToolsetDeps` создаётся с `Silent`, и `notifying()` в проде не зовётся. Сегодня эскалация
  видна через `immortality escalations`, а не тостом. Внешних каналов в v0.1 нет.
- `blocking: true` используется только когда без ответа физически нельзя продолжать
  ни одну подзадачу (например, `journal_corrupt`).

**Реализация (M3.8).** `blocking` — не аргумент модели: он выводится из `kind`, и только
`journal_corrupt` даёт `true` (D-067). Очередь — `escalations.json` в каталоге состояния
задачи, пишется атомарно. Повторный `escalate` с тем же `key` возвращает текущее состояние:
если вопрос уже отвечен, модель видит ответ в том же шаге и может действовать. `key`
нормализуется (trim) и ограничен 200 байтами — `external:push` и `external:push ` не должны
быть разными вопросами.

**Чего нет в проде.** Демон собирает `Escalate` с `DirectoryQueue`, у которой хуки
`opened`/`resolved` — пустые `Ok(())`: записи `escalation_opened` / `escalation_resolved` в
живой журнал не попадают, и живой журнал `black_jack` их действительно не содержит.
`JournalQueue`, которая пишет оба события, реализована и покрыта тестами, но к демону не
подключена (её `journal_dir` должен быть `.agent/` проекта, а очередь и журнал живут в разных
каталогах — это и есть причина отдельного типа). Следствие: `metrics`
`escalations_total`/`escalations_pending` и `closed_with_escalation` на живом журнале будут
нулевыми, а не «эскалаций не было».

## 5. Гейты DoD

Завершение проверяет система по `ACCEPTANCE.md`:

1. **Команды проверки** (сборка, тесты, линт) — исполняются, результат в журнал
   (`gate_result`). Красный гейт = подзадача не закрыта. Команда — одна программа, не пайп:
   `/bin/sh` берёт код возврата последней команды в трубе, поэтому `cargo test | tail -20`
   завершается `0` на несобранном коде. Проверка с неэкранированным `|` отклоняется при загрузке
   плана (D-116); `||` и пайп внутри кавычек — законны.

2. **Reviewer-субагент** с чистым контекстом: получает только diff и DoD, возвращает
   вердикт `approve` / `request_changes` со списком проблем. Не может править код сам.
3. **Дифф-санити**: нет случайных бинарников, нет секретов (эвристика по паттернам
   `API_KEY=`, приватные ключи), нет изменений в `.git/config`, нет правок глобального
   конфига, нет `TODO(agent)` без причины.

Только при трёх зелёных гейтах подзадача → `done`, а задача при всех закрытых подзадачах →
`ready_for_review`. Модель не может объявить успех в обход проверок.

Порядок — **дешёвое первым**: санити, команды, reviewer. Находка санити уже проваливает заявку и
обрывает остальное; красная обязательная команда обрывает оставшиеся команды и reviewer;
необязательная (`required: false`) не останавливает ничего. Отказ политики и таймаут — красная
проверка: «не запускалось» и «не доказано» не бывают зелёными. Reviewer получает только
`Dod.statement` и дифф, без инструментов; любой ответ, кроме явного `approve`, — `request_changes`,
включая прозу, неизвестный вердикт, пустоту и недоступный бэкенд. Дифф — против `HEAD` (или явной
базы) плюс untracked-файлы; слишком большой дифф — находка, а не усечение.

Раннер пишет по записи `gate_result` на гейт и закрывает **попытку**; `done` в `TASKS.json`
пишет планировщик (D-079).
