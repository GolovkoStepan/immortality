# immortality

Долгоживущий агент для программирования и работы с терминалом. Работает на локальных
моделях через OpenAI-совместимый HTTP API, живёт днями, переживает падения и не
залипает в бесконечных рассуждениях.

> **Статус: M5.8 завершена — прогон живёт в демоне; M6.1 завершена — тестовый репозиторий и
> три задачи; M6.3 — частично: метрики считаются из журналов, прогоны ждут бэкенд.**
> Workspace собирается, 1698 тестов зелёные, живая модель для тестов не нужна.
> `immortality start "<цель>"` доводит задачу до `ready_for_review` внутри демона: планирует,
> если плана нет, уважает правки человека без `--force`, держит слот прогона, строит worktree,
> ведёт журнал и публикует записи в `attach` из самого процесса записи. `kill -9` посреди
> подзадачи восстанавливается, недоступный бэкенд не убивает задачу. Готовы `PolicyGate`,
> чтение (`read_file`, `glob`, `grep`), запись (`write_file`, `edit_file`), `shell`, реестр
> процессов (`start_process`, `read_process`, `kill_process`), `git` с менеджером worktree
> на задачу, состояние (`read_state`, `update_state`, `grep_journal`), очередь эскалаций
> (`escalate`), делегирование (`delegate`), unix-сокет с клиентом (`status`,
> `escalations`, `approve`, `attach`) и `metrics` — числа вехи, посчитанные из журнала.
> `immortality serve` поднимает демон в foreground:
> файловая блокировка не даёт второму экземпляру снести сокет живого, токен чеканится
> один раз с правами `0600`, `SIGTERM` и Ctrl-C убирают сокет и блокировку, а рестарт
> после `kill -9` проходит по оставшемуся сокету (D-073). `attach` рисует поток блоками —
> намерение инструмента, его результат, ответ модели прозой, запрос к человеку с
> готовой командой ответа; цвет включается только на терминале, а разрыв связи печатается
> отдельной строкой, чтобы замерший экран не путался с «модель думает» (D-072).
> Симулятор убивает процесс в каждой точке протокола
> tool-call и доказывает, что восстановление корректно; клиент переживает все сценарии
> деградации бэкенда — 429, 5xx, обрыв посреди стрима, молчащий и зацикленный бэкенд.
> Контекст собирается так, что префикс промпта не двигается между шагами: слои рендерятся
> один раз, история растёт только в конец, а тест сравнивает сериализованный system-месседж,
> потому что именно его ключует кэш бэкенда. Компактация идёт по жёсткому шаблону из пяти
> секций и не может потерять отвергнутые гипотезы (D-074).
> План (`PLAN.md`, `ACCEPTANCE.md`, `TASKS.json`) валидируется целиком при загрузке: цикл,
> висячая зависимость, дубль id, `DoD` без гейта и совравший `depth` отвергаются до первого
> шага, а не через часы по симптому «нет готовой подзадачи». Правки человека подхватываются
> без рестарта по mtime+len (D-075).
> Runner исполняет одну подзадачу за попытку: строит свежий контекст, крутит шаги «вызов
> модели → инструменты», пишет журнал и возвращает отчёт, который наследует следующая
> попытка. Модель спрятана за трейтом, поэтому цикл тестируется без сети. Заявка
> `finish_subtask` не закрывает попытку: `Succeeded` означает «гейты прошли», и оценивать
> свою работу раннер не вправе. Каждая запись журнала несёт область
> `(subtask, attempt)`, иначе recovery не находит попытку, брошенную крахом. Тот же прогон
> проверен на живом бэкенде: 3 шага, заявка с осмысленным отчётом (D-076).
> Пять детекторов работают одновременно: точный повтор (D1), семантический повтор (D2),
> отсутствие прогресса (D3), цикл рассуждения (D4) и бюджет (D5). D1–D3 считают по истории
> шагов, D4 режет поток **до** конца сообщения — живой прогон срезал повтор на 161 символе
> из ~1200. Реакция — лестница: L1 дописывает подсказку в конец истории (префикс не
> двигается, кэш жив), L2 требует принудительный шаг с гипотезами, L3 кончает попытку.
> Каждое срабатывание — запись `detector_fired` с детектором, уровнем и метрикой, и
> нормальный прогон не даёт ни одной: тест на ложные срабатывания есть отдельно (D-077).
> Подзадачу можно дробить, но не глубже `max_subtask_depth`: модель **предлагает** куски
> инструментом `split_subtask` (только заголовок и цель), а решение принимает
> `core::scheduler`. DoD дети наследуют от родителя — модель, которая писала бы свои гейты,
> могла бы ослабить ровно ту гарантию, ради которой дробление и затевается. Отвергается
> дробление, теряющее обязательную проверку родителя (по id **и** по команде), теряющее
> ревьюера, выходящее за глубину, из одного куска (это та же работа под новым id с новым
> бюджетом попыток) и ребёнок, зависящий от родителя. `Blocked` считается закрытым, поэтому
> одна застрявшая подзадача не простаивает задачу; L5 эскалирует только когда после
> блокировки запускать действительно нечего (D-078).
> Заявка модели о готовности проходит три гейта. Сначала дифф-санити: бинарники, секреты,
> правки `.git/config`, пути за пределами worktree, `TODO(agent)` без причины и слишком
> большой дифф — находки, и любая из них проваливает заявку. Потом команды из DoD — отказ
> политики и таймаут считаются красной проверкой, необязательная проверка ничего не
> останавливает. Потом reviewer: он получает только формулировку DoD и дифф **без
> инструментов**, а одобряет только явный `approve` — проза, неизвестное слово, пустота и
> недоступный бэкенд это `request_changes`. Порядок «дешёвое первым» — это бюджет: находка в
> диффе уже провалила заявку, и платить за прогон тестов и вызов модели, чтобы сказать об
> этом, незачем. Правила — чистые функции в `core::gate`, весь I/O за трейтами `Gates` и
> `Reviewer`, поэтому порядок и короткое замыкание проверяются без репозитория и модели.
> Раннер закрывает попытку (`Succeeded` только при зелёном вердикте) и пишет по записи
> `gate_result` на гейт; `done` в `TASKS.json` пишет планировщик, потому что дерево — его
> (D-079).
> Провалившаяся попытка не заканчивает подзадачу: решение «ещё одна попытка» — чистая функция
> `core::restart::decide`, а git за швом `Checkpoints`. Решений два. Отказ гейта — `Retry`:
> дерево остаётся, потому что ревьюер прочитал дифф и назвал, что в нём не так, а откат выбросил
> бы почти готовую работу. Детектор, бюджет, стойло, пустой ответ и неизвестный инструмент —
> `Restart`: дерево откатывается к базовому чекпоинту. Оба списывают бюджет попыток, только
> `Restart` — ещё и бюджет перезапусков, причём до решения, поэтому бюджет в 2 попытки даёт
> ровно 2. Выброшенная работа не теряется: снимок и его SHA попадают в журнал **до**
> `git reset --hard`, затем `attempt_restarted`, и `recover` находит окно краха между ними по
> маркеру `checkpoint_created {role:"rollback"}` без подтверждения. В бриф следующей попытки
> идут причина (наблюдение и совет), исходная стратегия и накопленный `rejected_ideas`;
> сгенерированная стратегия не цитируется, иначе советы вкладываются сами себя (D-080).
> Симулятор прогоняет **настоящий** цикл — `Plan::load`, `AttemptSession::drive`,
> `core::gate::evaluate`, `core::scheduler` — и подменяет только границы: модель, гейты,
> reviewer и git. Сценарий доводит задачу до `ready_for_review` через зацикливание первой
> попытки, откат и вторую, зелёную. Время идёт не с машинных часов, а с часов журнала:
> `core::time::Clock` — `SystemClock` в продакшене, замороженный `FixedClock` в тестах и
> симуляторе, поэтому запись попытки «тратит 46 минут за ноль реальных секунд» проверяет
> 45-минутный бюджет без ожидания. Журнал полного цикла лежит в golden-файле и сравнивается
> нормализованным — `ts` как смещение от фикстуры, attempt-ULID как `att_1`, `att_2` — потому
> что побайтовое равенство невозможно без мока `Attempt::start`, а проверять хэш случайного id
> бессмысленно. Симулятор нашёл настоящий баг: запись `tool_call_intent` несла только
> аргументы инструмента, без `tool` и `idempotency`, и recovery настоящего журнала считала
> любой прерванный `write_file` неретрящимся и откатывала работу; теперь метаданные пишет сам
> `ToolCallLog`, а аргументы вложены, чтобы не подменить поле (D-081). По той же причине
> `expected_effect` в журнале — про этот вызов («write src/parser.rs», «run `cargo test`»), а
> не описание инструмента.
> Следующая веха — M5 (демон и CLI: lifecycle, launchd, команды целиком).

## Быстрый старт

```bash
cargo build
cargo test --workspace          # 1474 теста, живая модель не нужна
just ci                         # то же, что запускает GitHub Actions

# диагностика: конфиг, бэкенд, кэш префикса, место на диске, права на сокет
immortality doctor
immortality doctor --json

# создать .agent/ в текущем репозитории
immortality init

# поднять демон в foreground (второй терминал: immortality attach)
immortality serve
```

Первый `serve` сам чеканит `daemon.token` с правами `0600`; второй экземпляр на том же
каталоге состояния отказывает и называет pid держателя, не трогая сокет работающего демона.

`doctor` сообщает о попаданиях в префиксный кэш, потому что на этом бэкенде
раскладка промпта решает, стоит шаг одну секунду или девяносто.

## Идея в одном абзаце

Демон `immortality serve` держит состояние задачи, планировщик и агентный цикл.
Тонкий CLI-клиент подключается к демону по unix-сокету и может умирать/перезапускаться
в любой момент. Долговременная память задачи лежит в plain-файлах репозитория
(`.agent/`), а не в контексте модели: контекст считается расходным и пересобирается
из состояния. Каждый шаг журналируется, каждый инструмент объявляет идемпотентность,
перед рискованными действиями ставится git-чекпоинт. Сложная задача декомпозируется
в дерево подзадач, и каждая подзадача исполняется в свежем контексте — это главный
механизм борьбы с деградацией локальных моделей.

## Целевая среда

- macOS на Apple Silicon (M4, 16 ГБ unified memory — целевая dev-машина).
- Инференс — на отдельном ПК в LAN: Strata, `llm-server:47832`, OpenAI-совместимый `/v1`.
- Модель `swift-iq2_xs` (Swift 1.5 IQ2_XS), окно 256K, **рабочий бюджет промпта 32K/64K**.
- Замеры: prefill ~350 tok/s, decode ~35–65 tok/s, кэш префикса даёт ускорение до 400×.
  Подробности — в `docs/backend-check-swift-iq2xs.md`.

## CLI

Реализованы `doctor` и `init`; остальные команды объявлены и сообщают веху, в
которой появятся.

```
immortality init
immortality start "<цель>"        # создать задачу и запустить агентный цикл
immortality attach                # стрим событий блоками (стиль Claude Code, D-072)
immortality status                # состояние задач, подзадач, бэкенда
immortality plan                  # показать/отредактировать план
immortality escalations           # очередь запросов подтверждения
immortality log <task>            # человекочитаемый транскрипт прогона
immortality merge <task>          # влить ветку задачи (делает человек)
immortality gc                    # ротация и очистка тяжёлых артефактов
immortality doctor                # диагностика окружения и бэкенда
immortality serve                 # демон
```

## Принципы

1. **Состояние на диске — источник истины. Контекст модели — расходный материал.**
2. **Ни один шаг не выполняется дважды.** Идемпотентность объявляется инструментом,
   неидемпотентные вызовы после сбоя проверяются по факту, а не повторяются вслепую.
3. **Зацикливание обнаруживается и лечится ступенчато**: подсказка → смена стратегии →
   перезапуск попытки → блокировка подзадачи и переход к следующей.
4. **Необратимое — только через человека.** Push, сеть вне allowlist, удаление вне
   worktree и sudo уходят в очередь эскалаций; работа при этом продолжается.
5. **Политики безопасности не редактируются агентом.** Только глобальный конфиг.
6. **Всё тестируется без живой модели**: mock-сервер, симулятор прогонов, фейковые часы,
   golden-журналы, инъекция падений.
