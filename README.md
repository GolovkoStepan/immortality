# immortality

Долгоживущий агент для программирования и работы с терминалом. Работает на локальных
моделях через OpenAI-совместимый HTTP API, живёт днями, переживает падения и не
залипает в бесконечных рассуждениях.

> **Статус: v0.1.4.** Планка v0.1 выполнена и измерена: на живом прогоне агент закрыл три
> подзадачи подряд зелёными гейтами без вмешательства человека, пережил `kill -9` посреди
> шага и довёл задачу до `ready_for_review`. Числа считаются `immortality metrics` из
> журналов, а не пересказываются — см. [docs/metrics-v0.1.md](docs/metrics-v0.1.md).
>
> Веха `0.2` («петля не теряет найденное») **не доказана**: её критерий требует трёх чисел
> одновременно, и ни один из записанных прогонов не даёт всех трёх. Таблица прогонов и разбор —
> [docs/roadmap.md](docs/roadmap.md) §`0.2`; это записано, а не подразумевается.
>
> Workspace собирается, 1968 тестов зелёные, живая модель для тестов не нужна: производственный
> путь `start` с настоящими гейтами проверяется репетицией в `tests/dogfood.rs`.

## Установка

```sh
just install        # собрать release и положить `immortality` в ~/.local/bin
immortality --version
```

Рецепт собирает `target/release/immortality`, копирует его в `bindir` (по умолчанию
`~/.local/bin`, переопределяется `IMMORTALITY_BINDIR=/opt/homebrew/bin just install`) и **запускает
установленный бинарь**, чтобы «успех» не оказался копией вне `PATH`. Если каталога
нет в `PATH`, он печатает строку для `~/.zshrc` и не трогает ваш конфиг сам:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

`just uninstall` убирает только бинарь; состояние демона (`~/.local/share/immortality`, журналы,
конфиг, `daemon.token`) остаётся — удалять его молча было бы потерей ваших прогонов.

`cargo install --path crates/cli` тоже работает, но кладёт бинарь в `~/.cargo/bin`, которого на
этой машине нет в `PATH`; рецепт выбран потому, что проверяет, где бинарь оказался.

## Быстрый старт

```bash
just install                     # release-бинарь в ~/.local/bin, доступный как `immortality`
cargo test --workspace           # 1968 тестов, живая модель не нужна
just ci                          # все четыре джоба CI локально

# диагностика: конфиг, бэкенд, кэш префикса, место на диске, права на сокет
immortality doctor

# создать .agent/ и стартовый конфиг в текущем репозитории
immortality init

# поднять демон в foreground; во втором терминале — immortality attach
immortality serve

# поставить задачу и вести её до ready_for_review
immortality start "<цель>"

# посчитать числа вехи из журнала
immortality metrics
```

Первый `serve` сам чеканит `daemon.token` с правами `0600`; второй экземпляр на том же
каталоге состояния отказывает и называет pid держателя, не трогая сокет работающего демона.
Для фоновой работы есть `immortality service install` — `LaunchAgent` с `KeepAlive` на macOS
и `systemd --user`-юнит с `Restart=on-failure` на Linux; оба переживают ребут.

## Идея в одном абзаце

Демон `immortality serve` держит состояние задачи, планировщик и агентный цикл. Тонкий
CLI-клиент подключается к демону по unix-сокету и может умирать и перезапускаться в любой
момент. Долговременная память задачи лежит в plain-файлах репозитория (`.agent/`), а не в
контексте модели: контекст считается расходным и пересобирается из состояния. Каждый шаг
журналируется, каждый инструмент объявляет идемпотентность, а перед первой попыткой подзадачи
снимается скрытый git-чекпоинт, к которому откатывается провалившаяся попытка. Сложная задача
декомпозируется в дерево подзадач, и каждая подзадача исполняется в свежем контексте — это
главный механизм борьбы с деградацией локальных моделей.

## Команды

| Команда | Что делает |
| --- | --- |
| `immortality init` | Создаёт `.agent/`, проектный `config.toml` без политики и вписывает репозиторий в `registry.json` — единственная команда, которая пишет в состояние сама, потому что демона может ещё не быть |
| `immortality start "<цель>"` | Заводит задачу и запускает цикл. Отсутствующий план строит planner, существующий уважает (перестроить — `--force`) |
| `immortality start --task <id>` | Возобновляет существующую задачу с того состояния, которое называет журнал |
| `immortality attach [<task>]` | Стрим событий блоками: намерение инструмента, результат, проза модели, вопрос человеку. Догоняет журнал через `--since-seq` |
| `immortality status [<task>]` | Состояние задач, подзадач, бэкенда и причина простоя, если работа стоит |
| `immortality plan` | Показывает план так, как его читает демон |
| `immortality plan --goal "<цель>"` | Просит planner разложить цель в `PLAN.md` / `ACCEPTANCE.md` / `TASKS.json` |
| `immortality escalations [<task>]` | Очередь запросов подтверждения |
| `immortality approve <id> <answer>` | Ответ на эскалацию: `allow_once`, `allow_for_task` или `deny` |
| `immortality log [<task>]` | Человекочитаемый транскрипт прогона |
| `immortality metrics [<task>]` | Числа вехи из журнала: закрытия, серия, детекторы, эскалации, перезапуски |
| `immortality merge <task>` | Вливает ветку задачи. Делает человек, не агент |
| `immortality gc [--dry-run]` | Ротация логов и очистка тяжёлых артефактов |
| `immortality reset [--yes] [--token]` | Удаляет всё, что создала immortality: worktree, ветки `agent/*` и `agent-ckpt/*`, все `.agent/`, `state/`, артефакты, логи, реестр. Без `--yes` только перечисляет. Чужие коммиты и ветки не трогает |
| `immortality doctor` | Диагностика окружения и бэкенда; `--json` для машинного вида |
| `immortality serve` | Демон в foreground: файловая блокировка, сокет, токен, сигналы |
| `immortality service install\|uninstall\|status` | `LaunchAgent` (macOS) или `systemd --user`-юнит (Linux) для фонового демона; все три идемпотентны |

Глобальные флаги — `--json`, `--model`, `--base-url`, `--log-level`, `--global-config`,
`--project-config`. Они действуют в каждой подкоманде, включая `serve`: демон читает тот же
файл, который назвал человек, а не обнаруженный по умолчанию (D-118). `--project <path>` есть
только у `start` и `plan`: остальные команды адресуют задачу по `id`, а проект демон находит
через реестр.

Команды, которым нужно состояние прогона, — RPC-методы демона (D-088), а не чтение файлов
клиентом: только у демона есть лимит глубины плана, живой набор задач и право писать в
журнал. Это касается и пишущих: `gc` удаляет артефакты и крутит логи, `merge` вливает ветку
в текущую. Вне демона живут только `doctor` (диагностика процесса), `serve` (сам демон),
`service` (launchd или systemd — файлы службы, а не прогон) и `init` — последняя пишет в
`registry.json` напрямую, потому что регистрировать репозиторий может быть нужно до первого
запуска демона.

`reset` — тоже вне демона, и по той же причине, только с обратным знаком: команда,
приводящая машину к нулевому состоянию, не может зависеть от процесса, который этим
состоянием владеет. Она работает при остановленном демоне, при сломанном конфиге и при
демоне, который сам является частью мусора (D-146).

## Конфигурация

Приоритет (позже сильнее): дефолты → глобальный конфиг → проектный конфиг → env
(`IMMORTALITY_*`) → флаги CLI.

- **Глобальный** `~/Library/Application Support/immortality/config.toml` — единственное место,
  где живут политики безопасности: `workspace_root`, `trusted_hosts`, `deny_read_globs`,
  `deny_write_globs`, `deny_programs`, `yolo` и флаги разрешений. Агент в него не пишет.
- **Проектный** `<repo>/.agent/config.toml` — профили моделей, бюджеты контекста, лимиты
  цикла, пороги детекторов, логи и хранение. Прав может не расширять: секция `[policy]`
  в проектном файле игнорируется с предупреждением.

Оба файла парсятся с `deny_unknown_fields`, поэтому опечатка — ошибка, а не тихий дефолт.
Проектный файл применяется на **задачу**, а не на процесс демона: под launchd рабочий каталог —
`/`, и искать `.agent/config.toml` от него бессмысленно (D-119). Полный разбор ключей и значений —
[docs/design.md](docs/design.md) §3.

## Проверки: что запускать перед коммитом и перед тегом

Есть два разных гейта, и путать их дорого: `v0.1.3` был помечен тегом при красном CI, потому что
локальный гейт состоял из трёх проверок, а в CI их было четыре.

### Перед коммитом

```sh
cargo fmt --all
cargo clippy --workspace --all-targets --offline
cargo test --workspace --offline
```

Это быстро и покрывает то, что ломается от правки. `--offline` здесь законен: локальный кэш
тёплый, а сеть для компиляции не нужна.

### Перед тегом или push — всё, что делает CI

```sh
just ci
```

`just ci` = `fmt-check` + `lint` + `test` + `audit` + `layering`, то есть **все четыре джоба**
воркфлоу. Если `just` не установлен (`brew install just`), те же команды по одной:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features

# джоб `dependencies`: база уязвимостей, дубликаты версий, лицензии, источники
cargo deny check advisories bans licenses sources

# джоб `crate layering`: ядро остаётся синхронным и без HTTP-клиентов
grep -E '^(tokio|reqwest|hyper|immortality-daemon|immortality-tools)' crates/core/Cargo.toml \
  && echo "core must stay free of async/HTTP dependencies" && exit 1
```

Проверка зависимостей — **единственная**, которую нельзя запустить офлайн: `cargo deny` тянет
базу RustSec из сети, и именно поэтому она меняет результат без коммитов. Запись `RUSTSEC-2026-0543`
(`chrono` неподдерживаем) появилась 2026-11-17 и покрасила уже выпущенный тег. Отсюда правило:
**перед тегом `just ci` целиком, а не только `cargo test`.**

`cargo deny` установлен не всегда: `cargo install cargo-deny --locked`, версия 0.20.2 или новее
(конфиг использует `unmaintained`/`unsound` как строки, в старых это другие ключи).

Паритет локального гейта и CI проверяется тестом, а не обещанием:
`crates/daemon/tests/ci_contract.rs` парсит `justfile` и `.github/workflows/ci.yml` и падает, если
в CI появился джоб без рецепта в `just ci`, если `audit` перестал запускать полный набор проверок
или если запись в `ignore` (`deny.toml`) осталась без ссылки на решение `D-NNN` (D-143).

### Linux

`just ci` идёт на macOS и о Linux-джобе молчит. Перед релизом полезно прогнать хотя бы `test` в
контейнере — рецепт и три неочевидные детали в [docs/linux-check.md](docs/linux-check.md).

## Целевая среда

- macOS на Apple Silicon (M4, 16 ГБ unified memory — целевая dev-машина).
- Инференс — на отдельном ПК в LAN: Strata, `llm-server:47832`, OpenAI-совместимый `/v1`.
- Модель `swift-iq2_xs` (Swift 1.5 IQ2_XS), окно 256K, **рабочий бюджет промпта 32K/64K**.
- Замеры: prefill ~350 tok/s, decode ~35–65 tok/s, кэш префикса даёт ускорение до 400×.
  Подробности — в [docs/backend-check-swift-iq2xs.md](docs/backend-check-swift-iq2xs.md).

## Что v0.1 не делает

Честный список, чтобы README не обещал больше кода:

- **Демон сам задачу не подхватывает.** `start` — явное действие; после простоя бэкенда
  прогон продолжается через `immortality start --task <id>`. Очередь планировщика умеет
  ранжировать кандидатов, но диспетчера, который бы её исполнял, нет.
- **Push, merge в `main`, релизы — человек.** `immortality merge` вливает ветку задачи в
  текущую ветку репозитория, но push и решение о релизе остаются за человеком.
- **Нет PTY, веб-клиента, RAG и мультипроектного планировщика в одном демоне.** Полный
  список — [docs/non-goals-v0.1.md](docs/non-goals-v0.1.md).
- **Часть механики реализована, но не подключена к прогону**: health-check, backoff в
  демоне, эскалация по 15-минутному простою, офлайн-работа, диск-гард `paused_disk`,
  компактация контекста, перечитывание плана по `mtime`, второй слот инференса
  (`max_inference_concurrency`). В этом списке больше нет судьи, `delegate`, macOS-нотификаций
  и `JournalQueue` — они подключены. Таблица «что где живёт, чего нет» и веха для каждого
  пункта — [docs/roadmap.md](docs/roadmap.md) §M6.
- **Отказ политики не задаёт вопроса человеку.** `Verdict::Escalated` из `check_command` —
  это отказ с честным текстом, а не запись в очередь; вопрос задаёт инструмент `escalate`
  (D-141). Ответ человека до модели тоже не доходит: `server::approve` пишет в
  `escalations.json`, а `blocking_question` из прода не зовётся — это веха `0.3`.
- **`yolo = true` снимает вопрос и у `git push`, и у `curl`.** Это расходится с обещанием
  «push — человеку», хотя формально не нарушает «флаг снимает вопрос, а не запрет». Два
  расхождения такого рода записаны в `CHANGELOG.md` §«Известные ограничения» (D-138, D-139).

## Принципы

1. **Состояние на диске — источник истины. Контекст модели — расходный материал.**
2. **Ни один шаг не выполняется дважды.** Идемпотентность объявляется инструментом,
   неидемпотентные вызовы после сбоя проверяются по факту, а не повторяются вслепую.
3. **Зацикливание обнаруживается и лечится ступенчато**: подсказка → смена стратегии →
   перезапуск попытки → блокировка подзадачи и переход к следующей.
4. **Необратимое — только через человека.** Push, сеть вне allowlist, удаление вне
   worktree и sudo уходят в очередь эскалаций; работа при этом продолжается.
5. **Политики безопасности не редактируются агентом.** Только глобальный конфиг.
6. **Всё тестируется без живой модели**: mock-сервер, симулятор прогонов, фейковые часы,
   golden-журналы, инъекция падений.
